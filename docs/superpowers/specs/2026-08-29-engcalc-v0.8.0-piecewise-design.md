# EngCalc 0.8.0 Piecewise Expressions — Design

## Status

- Design approved globally in chat on 2026-08-29.
- This document is the formal written specification for user review before implementation planning.
- Implementation has not started.
- Package/runtime version remains 0.7.2 until formal release closure.

## Baseline

EngCalc 0.7.2 is the canonical `main` baseline. It already provides:

- restricted AST-based symbolic DSL;
- separate Pint-backed numerical context;
- `numeric(...)` detailed calculation-memory rendering;
- `result(...)` compact rendering;
- scalar engineering mathematics;
- one-or-more-argument user functions and generalized partial evaluation;
- native `plot(...)`, parameter sweeps and sampled envelopes;
- native engineering `table(...)` output;
- `integral(...)`, `diff(...)`, `simplify(...)`, `expand(...)`, `factor(...)`, `subs(...)` and `solve(...)` through restricted symbolic evaluation;
- 201-point plot/envelope base sampling;
- positive structural moment plotted downward.

0.8.0 extends this language with safe symbolic functions whose values change by explicit interval.

## Goal

Make loads, section properties, response functions and other engineering quantities that change by interval first-class EngCalc expressions while preserving:

1. the symbolic/numerical separation;
2. Pint unit safety;
3. restricted parser safety;
4. compatibility with existing numerical, table, plotting and calculus workflows;
5. exact breakpoint awareness where the user explicitly provides the breakpoint;
6. existing 0.7.2 behavior as a regression baseline.

Typical examples include distributed loads that change along a beam, piecewise shear/moment laws, sectional-property changes, layered properties and engineering operating regimes.

## Primary syntax

```text
q(x) = piecewise(
    q1, x < a,
    q2, x <= L,
    0
)
```

General form:

```text
piecewise(
    value_1, condition_1,
    value_2, condition_2,
    ...,
    default_value
)
```

The call requires:

- at least one `value, condition` pair;
- one final default expression;
- an odd number of positional arguments greater than or equal to 3;
- no keyword arguments.

The final default is mandatory. EngCalc never silently invents a zero branch.

`piecewise` becomes a reserved EngCalc function name and may not be redefined as a scalar, user function or user-function parameter.

## Branch ordering and boundary ownership

Branches are evaluated in source order. The first condition that evaluates true governs. If no condition is true, the mandatory default branch governs.

Example:

```text
q(x) = piecewise(q1, x < a, q2, x <= L, 0)
```

means effectively:

```text
q1   for x < a
q2   for a <= x <= L
0    otherwise
```

At `x = a`, the first condition is false and the second may be true, so `q2` governs.

Changing the first condition to `x <= a` intentionally assigns the boundary to the first branch.

EngCalc does not impose its own endpoint convention; the user's comparison operator is authoritative.

## Allowed conditions in 0.8.0

0.8.0 deliberately supports only explicit interval boundaries that can be identified without solving an equation.

Allowed comparison operators:

```text
<
<=
>
>=
```

A condition must be one binary comparison between:

- the piecewise/plot variable on one side; and
- a breakpoint expression that does not contain that same variable on the other side.

Examples:

```text
x < a
x <= L
x >= x0
a < x
x < L/2
x >= a + d
```

The comparison may be written in either orientation. `a < x` and `x > a` are both valid.

The breakpoint expression may contain other symbols or scalar arithmetic, provided it does not contain the compared variable.

The following are not supported in 0.8.0:

```text
0 <= x < a
x > 0 and x < a
x < a or x > b
not(x < a)
M(x) > 0
sin(x) <= 0
f(x) < g(x)
```

Also unsupported as public Piecewise conditions:

```text
==
!=
is
in
and
or
not
```

Conditions such as `M(x) > 0` require root finding; `f(x) < g(x)` requires intersections. Those belong to the planned 0.8.1 exact-first roots/intersections/extrema subsystem rather than being hidden inside 0.8.0.

## Parser safety

`ast.Compare` is not globally enabled.

It is whitelisted only in Piecewise condition positions and only when:

- exactly one comparator exists;
- the operator is `<`, `<=`, `>` or `>=`;
- one side is a direct symbolic variable;
- the opposite side is a restricted EngCalc scalar expression that does not contain that variable.

Therefore a standalone comparison such as:

```text
A = x < a
```

remains invalid unless a later feature explicitly adds comparison values as a public construct.

General Python conditionals, ternaries, lambdas, comprehensions and arbitrary boolean expressions remain rejected.

## Symbolic representation

SymPy `Piecewise` is the authoritative symbolic representation.

EngCalc constructs explicit SymPy relational nodes (`Lt`, `Le`, `Gt`, `Ge`) and Piecewise branches instead of creating a separate algebra system.

The implementation should preserve source-order branch semantics and preserve the user's comparison orientation for display when safely possible. Relations should be constructed without eager canonicalization where needed so that a user-written `x < a` is not unnecessarily rendered as `a > x`.

The final default is represented symbolically as an unconditional branch.

Nested Piecewise expressions are allowed as ordinary branch-value expressions. They do not introduce new condition syntax. Breakpoint inspection traverses nested Piecewise values recursively.

## Symbolic/numeric separation and dimensional breakpoints

EngCalc keeps units in the Pint numerical context rather than treating unit names as symbolic constants.

Recommended and supported form:

```text
a := 3*m
L := 6*m

q(x) = piecewise(q1, x < a, q2, x <= L, 0)
```

0.8.0 does not add unit literals directly to symbolic Piecewise conditions such as:

```text
x < 3*m
```

This avoids giving identifiers like `m` a second meaning inside symbolic conditions and preserves the existing symbolic/numeric namespace boundary.

Breakpoint names and expressions are resolved numerically when a numerical operation requires them.

## Numeric condition evaluation

Numeric comparison is performed through Pint quantities.

Compatible units are normalized before comparison:

```text
x = 2*m
a := 300*cm
```

allows `x < a` to evaluate correctly.

An exact dimensionless zero may inherit the dimensionality of the other side of a comparison. Thus `x >= 0` is valid when `x` is a dimensional quantity.

A nonzero dimensionless value compared against a dimensional quantity is rejected as ambiguous.

Dimensionally incompatible comparisons, such as a length against a force, raise an engineering-facing error rather than stripping units.

## Branch-unit compatibility

Piecewise is one physical response. Numerically evaluable branches must therefore be dimensionally compatible.

Valid conceptually:

```text
8*kN/m
4000*N/m
0
```

Invalid:

```text
8*kN
4*m
0
```

Also invalid:

```text
8*kN/m
3
0
```

when `3` is a nonzero dimensionless branch.

An exact dimensionless zero is special: when other evaluable branches establish a common dimensional unit, the zero inherits that unit.

Unit validation is performed when enough numerical context exists. Symbolic function definition itself does not require EngCalc to know every branch quantity numerically.

EngCalc must not blindly evaluate mathematically inactive branches at a point merely to determine units when doing so could cause a false domain error. Unit normalization should be branch-aware and should prefer established dimensional branch units over a leading dimensionless zero.

## Fully numeric evaluation

Example:

```text
q(x) = piecewise(q1, x < a, q2, x <= L, 0)

q1 := 8*kN/m
q2 := 4*kN/m
a := 3*m
L := 6*m

numeric(q(2*m))
```

The evaluator binds the function arguments, evaluates Piecewise conditions in order, evaluates only the governing branch as the response value, normalizes its unit and returns the normal `numeric(...)` result.

Expected values:

```text
numeric(q(2*m))  -> 8 kN/m
numeric(q(5*m))  -> 4 kN/m
numeric(q(8*m))  -> 0 kN/m
```

The default zero in the last example inherits the compatible response unit.

Target-unit conversion remains available for fully numeric results:

```text
numeric(q(2*m), N/m)
```

## Partial `numeric(...)` and `result(...)`

A free Piecewise variable remains symbolic while known branch data and breakpoints are substituted.

Example:

```text
numeric(q(x))
```

with known `q1`, `q2`, `a` and `L` should render conceptually as:

```text
formula
= Piecewise with known values/breakpoints substituted
= evaluated Piecewise form when EngCalc can produce it safely
```

The useful target presentation is equivalent to:

```text
8.00 kN/m   for x < 3.00 m
4.00 kN/m   for x <= 6.00 m
0.00 kN/m   otherwise
```

while preserving `x` as unresolved.

`result(q(x))` uses the same evaluation semantics but omits the explicit substitution stage, consistent with the existing distinction between `numeric(...)` and `result(...)`.

Polynomial branch expressions may reuse the current evaluated-coefficient logic branch by branch. Non-polynomial branches preserve the known substitution and remaining symbolic structure rather than inventing a compact numerical form.

Target-unit conversion remains forbidden when unresolved symbols remain.

## Table integration

Piecewise works as a normal table response:

```text
table(q(x), x, 0, L, 21)
```

The 0.7.2 table contract does not change:

- uniform-count tables contain exactly the requested count, including both endpoints;
- Piecewise breakpoints do not add extra rows;
- explicit-point tables contain exactly the user-supplied points;
- the table variable remains a temporary local numeric override;
- source order and response-column compatibility remain unchanged.

Each requested table point evaluates the appropriate Piecewise branch.

If a requested table point lies at a Piecewise boundary, the user's `<`, `<=`, `>` or `>=` condition determines the governing value.

## Plot and envelope integration

The existing 201-point plot/envelope grid remains the base renderer sampling policy.

For Piecewise responses, EngCalc augments that base grid with every numerically resolvable explicit breakpoint inside the requested plot domain.

Conceptually:

```text
final_plot_grid = 201-point base grid + exact Piecewise breakpoints
```

Breakpoints already present in the base grid are deduplicated.

For multiple plotted responses, the shared x-grid is the union of all Piecewise breakpoints so that all response series remain aligned.

For parameter sweeps, if a breakpoint depends on the swept parameter, the shared x-grid is the union of the resolvable breakpoints for every sweep case.

Existing envelope calculations use that aligned enriched grid but remain sampled envelopes in 0.8.0. Exact crossover/governing-interval logic remains 0.8.2 scope.

### Discontinuity rendering

The plotting renderer must not connect two Piecewise branches across an explicit Piecewise transition with an artificial line segment.

Each response carries enough breakpoint/segment information for Matplotlib rendering to split the polyline at Piecewise transitions.

This rule applies even if adjacent branches happen to be continuous; splitting a continuous curve at the same coordinate is visually harmless and avoids having to prove continuity during plotting.

0.8.0 does not add open/closed endpoint markers or special jump glyphs. The exact value at a breakpoint still follows source-order condition semantics.

The positive-structural-moment-down convention remains unchanged.

## Breakpoint extraction

A Piecewise breakpoint is extractable in 0.8.0 only when the condition directly compares the active plotting variable against a breakpoint expression that does not contain that variable.

Examples with variable `x`:

```text
x < a        -> breakpoint a
a < x        -> breakpoint a
x <= L/2     -> breakpoint L/2
x >= a + d   -> breakpoint a + d
```

EngCalc does not solve transformed inequalities such as:

```text
2*x < a
M(x) > 0
```

for hidden breakpoint locations in 0.8.0.

If a Piecewise expression is otherwise symbolically valid but a plot cannot extract a required breakpoint under the 0.8.0 rules, EngCalc raises a corrective diagnostic rather than silently pretending the 201-point grid is exact.

## `integral(...)`

EngCalc continues to delegate symbolic integration to SymPy.

```text
integral(q(x), x, 0, L)
```

constructs the normal symbolic integral input and calls SymPy on the Piecewise expression.

EngCalc does not create a separate Piecewise integrator.

SymPy may legitimately return Piecewise expressions or helper constructs such as `Min`/`Max` when symbolic limits do not establish an interval ordering. 0.8.0 numeric evaluation therefore supports the restricted SymPy relational/Piecewise/Min/Max forms produced by the supported calculus path when evaluating a resulting expression numerically.

The stored numerical context does not silently alter symbolic integration assumptions. For example, `a := 3*m` does not cause a symbolic `integral(..., 0, L)` to assume `0 < a < L` unless the numerical operation itself is being evaluated.

## `diff(...)`

Differentiation is branchwise and does not introduce `DiracDelta` automatically.

EngCalc does not pretend that an ordinary derivative exists exactly at a Piecewise transition merely because one branch owns the endpoint.

For 0.8.0, explicit Piecewise breakpoints are treated conservatively as derivative-undefined locations unless simplification has removed the Piecewise transition before differentiation.

Consequences:

- symbolic derivative branches are produced normally;
- `numeric(diff(...))` at a Piecewise breakpoint raises a clear undefined-derivative diagnostic;
- plots of such derivatives split at the breakpoint instead of connecting across it;
- ordinary numerical evaluation away from breakpoints uses the corresponding branch derivative;
- no distributional derivative or automatic delta term is created.

0.8.0 does not attempt a general proof of continuity or differentiability across different branch laws.

## Other symbolic operations

`piecewise(...)` composes with:

```text
simplify(...)
expand(...)
factor(...)
subs(...)
integral(...)
diff(...)
```

when SymPy can perform the operation under the restricted EngCalc expression model.

`solve(piecewise(...))` is not promoted as a new 0.8.0 contract. Root and intersection workflows belong to 0.8.1.

## Rendering

Symbolic Piecewise definitions render as native MathJax cases rather than Python-like function-call text where SymPy's Piecewise LaTeX representation is available.

Example target presentation:

```text
q(x) = {
  q1, x < a
  q2, x <= L
  0, otherwise
}
```

Existing semantic spacing remains:

- wrapped rows inside the same stage use the current continuation spacing;
- formula → substitution → result remains distinct for `numeric(...)`;
- formula → result remains compact for `result(...)`;
- headings, equations, tables and plots retain source order.

Partial numeric Piecewise rendering must format substituted branch quantities and breakpoint quantities using the active `precision` and `zero_tolerance` settings.

## Architecture

The implementation should use a hybrid architecture rather than placing all logic into `engine.py` or implementing an independent algebra system.

Recommended production responsibilities:

```text
parser.py
    Piecewise call-shape validation
    restricted Compare whitelist
    reserved identifier handling

piecewise.py
    symbolic Piecewise construction helpers
    condition inspection
    breakpoint extraction
    branch/segment metadata helpers

numeric.py
    Pint-aware relation evaluation
    Piecewise branch evaluation
    zero-unit inheritance
    restricted Min/Max support produced by supported calculus

engine.py
    orchestration with user functions, numeric/result, table, plot/envelope,
    integral/diff and existing state

models.py
    add only the minimal plotting/partial-result metadata required to carry
    Piecewise segment/breakpoint information across layer boundaries

renderer.py
    MathJax Piecewise and partial-numeric Piecewise presentation

plotting.py
    split plotted lines at Piecewise transitions; preserve existing styling,
    characteristic labels and moment convention
```

No new runtime dependency is required. SymPy, Pint and Matplotlib remain sufficient.

## Error behavior

Engineering-facing diagnostics should distinguish at least:

- malformed Piecewise arity;
- missing default branch;
- unsupported condition operator;
- chained comparison;
- boolean composition (`and/or/not`);
- condition not expressed as direct variable vs breakpoint;
- breakpoint still unresolved when a numerical plot/evaluation requires it;
- condition-side unit incompatibility;
- incompatible branch result units;
- ambiguous nonzero dimensionless branch mixed with dimensional branches;
- target-unit conversion requested for a partial Piecewise result;
- derivative requested numerically exactly at an undefined Piecewise transition.

When a safe correction is clear, the error includes a concrete example.

### Real `%%eng` acceptance

At least one engineer-facing cell must combine several layers, for example:


The acceptance test verifies source order and the expected result type/output for each operation.

## Release discipline

- Package/runtime version remains 0.7.2 during feature implementation.
- Release version becomes 0.8.0 only in the formal closing task.
- Focused tests run after each RED→GREEN slice.
- Full source suite runs at implementation gates.
- Release closure must build the real wheel, install it into a clean virtual environment, run an external smoke test outside the repository tree, run the full suite against the installed wheel, repeat the source suite, and remove temporary validation workflows before merge.
- No manual Codex/Codex Cloud invocation without explicit user authorization.
- Planning/feature branches are retained unless the user explicitly requests deletion.

## Explicitly out of scope for 0.8.0

- `and`, `or`, `not` Piecewise conditions;
- chained comparisons;
- public `==` / `!=` Piecewise conditions;
- arbitrary Python `if` / ternaries / lambdas;
- implicit root solving for conditions such as `M(x) > 0`;
- implicit intersections for conditions such as `f(x) < g(x)`;
- transformed-inequality breakpoint solving such as `2*x < a`;
- automatic Dirac-delta/distributional derivatives;
- Heaviside as a new public EngCalc API;
- open/closed endpoint plot markers;
- exact extrema/roots/intersections (0.8.1);
- exact envelopes/governing intervals (0.8.2);
- named cases/combinations (0.8.3);
- vectors/matrices (0.9.0);
- engineering checks/summaries (0.10.x);
- arbitrary Python execution.

## Success criteria

0.8.0 is ready for release closure only when an engineer can define a Piecewise response with dimensional breakpoint data and then safely use that same function through `numeric`, partial `numeric`, `result`, `table`, `plot`, `envelope`, `integral`, `diff`, and the supported symbolic transforms without bypassing EngCalc's restricted DSL or unit model.

The new capability must preserve every released 0.7.2 contract, including table count semantics, plot conventions, calculation-memory presentation and package/runtime separation.
