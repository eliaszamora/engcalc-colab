# EngCalc 0.7.2 Engineering Tables Design

## Status

Approved design for the next EngCalc milestone after the merged 0.7.1 baseline.

Baseline:

- canonical branch before this work: `main`;
- baseline release: EngCalc 0.7.1;
- 0.7.1 already supports the restricted symbolic DSL, Pint-backed numeric state, scalar engineering math, multi-argument user functions, generalized partial numeric evaluation, native plotting and envelopes.

This design intentionally keeps EngCalc a restricted engineering DSL. It does not introduce arbitrary Python evaluation or general-purpose list syntax.

## Goal

Make pointwise engineering evaluation a first-class EngCalc output so users can inspect response values directly inside `%%eng` without writing Python/pandas validation code.

The primary workflow is automatic uniform discretization. Explicit point lists remain available when the engineer needs specific evaluation locations.

## User-facing syntax

### 1. Primary form — automatic discretization

```text
L := 5*m
qD := 4*kN/m
M(x, q, L) = q*x*(L-x)/2
M_D(x) = M(x, qD, L)

table(M_D(x), x, 0, L, 21)
```

Interpretation:

- evaluate `M_D(x)` from `x = 0` through `x = L`;
- generate exactly 21 uniformly spaced points, including both endpoints;
- because `L` is dimensional, the exact dimensionless zero inherits the compatible endpoint unit instead of forcing the user to write `0*m`.

Multiple compatible responses are supported:

```text
table(M_D(x), M_L(x), M_U(x), x, 0, L, 21)
```

The final four positional arguments are always:

```text
variable, lower, upper, count
```

All preceding positional arguments are response expressions.

### 2. Explicit points with one declared unit

```text
table(M_D(x), x, [0, 1, 1.5, 2, 3, 4, 5], m)
```

Interpretation:

- the point list contains magnitudes;
- the final `m` applies to those point values;
- EngCalc therefore evaluates at `0*m`, `1*m`, `1.5*m`, etc. without requiring the unit to be repeated.

Multiple compatible responses are also allowed:

```text
table(M_D(x), M_U(x), x, [0, 1, 2, 3, 4, 5], m)
```

### 3. Fully explicit point quantities

```text
table(M_D(x), x, [0*m, 50*cm, 1*m, 150*cm, 2*m])
```

This form remains useful when points intentionally use mixed but compatible units. EngCalc normalizes them to one consistent variable unit for output and evaluation.

## Unit semantics

### Uniform range

For:

```text
table(response, x, lower, upper, count)
```

EngCalc resolves `lower` and `upper` through the existing Pint-backed numeric context.

Rules:

1. If both endpoints are dimensionally compatible quantities, they are normalized to one common unit.
2. If one endpoint is an exact dimensionless zero and the other endpoint is dimensional, zero inherits the dimensional endpoint unit. Therefore `table(M(x), x, 0, L, 21)` is valid when `L := 5*m`.
3. A nonzero dimensionless endpoint cannot silently inherit a dimensional unit. `table(M(x), x, 1, L, 21)` is rejected when `L` has length units; the diagnostic tells the user to write `1*m` or otherwise supply a compatible dimensional expression.
4. If both endpoints are dimensionless, the domain remains dimensionless. EngCalc never assumes metres or any other unit merely because the variable is named `x`.
5. Incompatible endpoint dimensions are rejected before row evaluation.
6. Descending ranges are allowed; generated points preserve the requested lower-to-upper order.

### Explicit list with declared unit

For `table(response, x, [p1, p2, ...], unit)`:

- dimensionless point expressions are multiplied by the declared unit conceptually;
- already-dimensional point expressions, if present, must be compatible with the declared unit and are converted to it;
- incompatible point dimensions are rejected with the offending point identified;
- the declared unit is the canonical variable-column unit.

### Fully explicit list

For `table(response, x, [p1, p2, ...])`:

- dimensional points must be mutually compatible;
- the first dimensional point establishes the canonical variable unit;
- exact dimensionless zero may inherit that canonical unit;
- nonzero dimensionless points mixed with dimensional points are rejected as ambiguous and the diagnostic recommends the one-unit form;
- if every point is dimensionless, the variable column remains dimensionless.

## Response semantics

Each response expression is evaluated independently at each table point by temporarily binding only the requested table variable.

Required behavior:

- stored symbolic values and numeric assignments are not mutated;
- user functions, including multi-argument functions from 0.7.1, work normally;
- nested user functions work normally;
- scalar engineering math from 0.7.0 works normally;
- existing numeric context values are available during evaluation;
- a constant response is valid and repeats across rows;
- if symbols other than the table variable remain unresolved at a row, table evaluation fails with a diagnostic naming the unresolved dependencies;
- evaluation must produce a fully numeric result at every requested point.

For 0.7.2, multiple response expressions in one table must be dimensionally compatible with each other. Cross-dimension tables such as moment + shear + displacement are deferred for a later design amendment.

## Count semantics

For the automatic discretization form:

- `count` must resolve to a dimensionless integer;
- booleans are not accepted;
- `count >= 2`;
- exactly `count` points are generated;
- both endpoints are always included;
- spacing is uniform in the normalized endpoint unit;
- a non-integer, dimensional, unresolved, or smaller-than-two count is rejected with a corrective example.

No Cartesian multi-parameter sweep is introduced.

## Parser and DSL safety

`table` becomes a reserved EngCalc public function name.

The parser must continue rejecting arbitrary lists everywhere except whitelisted table-point positions and the already-whitelisted plot/envelope sweep syntax.

Accepted table AST shapes are restricted to exactly these families:

```text
table(response[, response...], variable, lower, upper, count)
table(response[, response...], variable, [points...])
table(response[, response...], variable, [points...], unit)
```

Parser rules:

- at least one response expression is required;
- the table variable must be a symbolic identifier, not an arbitrary expression;
- point lists must be non-empty;
- list comprehensions, generator expressions, sets, dictionaries and nested lists remain unsupported;
- keyword arguments remain unsupported;
- `table(...)` is standalone only and cannot be assigned to a symbolic or numeric target;
- the parser must produce targeted syntax diagnostics rather than opening general Python list support.

## Result model

Introduce dedicated immutable table result structures instead of reusing `PlotResult`:

```text
TableColumn
- display_label
- unit
- values

TableResult
- statement
- variable
- point_unit
- point_values
- columns
- mode  # "uniform" | "explicit"
```

The table result is a presentation/evaluation result only. It does not mutate EngCalc state.

## Engine architecture

The AST dispatcher in `engine.py` recognizes `table(...)` as a first-class display/evaluation operation, analogous to plot/envelope dispatch but returning `TableResult`.

To avoid expanding the already-large evaluator with unrelated grid/unit mechanics, 0.7.2 isolates reusable table-specific logic in a focused module when practical:

- parser: validate restricted table call shape and table-specific list allowance;
- engine: resolve symbolic response expressions, table variable and existing EngCalc state;
- numeric/table helper: normalize points/range units, generate the grid and evaluate rows;
- models: immutable table result structures;
- renderer/magic: HTML table presentation inside `%%eng`.

No new runtime dependency is required; use existing Python, SymPy and Pint capabilities.

## Rendering inside `%%eng`

A table is rendered as an HTML table in source order.

Presentation requirements:

- one variable column followed by response columns in the exact order written by the user;
- one row per explicit/generated point, in evaluation order;
- consistent numerical formatting using existing EngCalc `precision` and `zero_tolerance` settings;
- units shown once in column headers rather than repeated in every cell when the column has a non-dimensionless unit;
- dimensionless columns omit a unit suffix;
- mathematical response labels use existing EngCalc display naming where practical;
- the table coexists correctly with headings and ordinary equation results in the same `%%eng` cell;
- blank-line spacing/source-order behavior remains coherent with existing output;
- no interactive spreadsheet behavior is required in 0.7.2.

Conceptual rendering:

```text
x [m] | M_D(x) [kN·m] | M_U(x) [kN·m]
------------------------------------------------
0.00  | 0.00          | 0.00
0.25  | ...           | ...
...   | ...           | ...
5.00  | 0.00          | 0.00
```

## Diagnostics

Table-specific failures distinguish at least:

- unsupported table call shape;
- missing response expression;
- invalid table variable;
- empty explicit point list;
- incompatible point/range units;
- ambiguous nonzero dimensionless point mixed with dimensional points;
- invalid count;
- unresolved response dependencies after binding the table variable;
- incompatible response dimensions;
- assignment of `table(...)` to a target.

When correction is safe to infer, diagnostics include supported examples such as:

```text
Use table(M(x), x, 0, L, 21) when L already carries the domain unit.
Use table(M(x), x, [0, 1, 2], m) to declare the point unit once.
```

## Backward compatibility

0.7.2 must not change symbolic `=`, numeric `:=`, `numeric(...)`, generalized partial evaluation, scalar engineering math, multi-argument user-function semantics, plot/envelope public syntax, 201-point plot/envelope policy, positive structural moment downward, or current precision/zero-tolerance behavior.

The fact that lists become valid in one `table(...)` position must not make list literals valid elsewhere in the DSL.

## TDD acceptance contracts

Implementation begins with RED tests. At minimum:

1. `L := 5*m; q := 4*kN/m; M(x,q,L)=q*x*(L-x)/2; table(M(x,q,L),x,0,L,21)` gives 21 rows, endpoints 0 and 5 m, midpoint 2.5 m, response 12.5 kN*m;
2. multiple compatible responses preserve source column order;
3. `0` inherits the other dimensional range endpoint unit;
4. nonzero dimensionless + dimensional range endpoint is rejected;
5. explicit magnitude list plus one unit works;
6. fully explicit mixed compatible units normalize correctly;
7. dimensionless explicit tables remain valid;
8. incompatible points are rejected;
9. count 1, non-integer count and dimensional count are rejected;
10. unresolved non-table dependencies are reported;
11. table evaluation does not mutate stored table variable or other state;
12. arbitrary list literals outside table remain rejected;
13. list comprehensions/nested lists in table remain rejected;
14. assignment to `table(...)` is rejected;
15. renderer outputs HTML table with units in headers and existing precision/zero-tolerance formatting;
16. real `%%eng` acceptance verifies mixed equations/headings/table source order;
17. all 0.7.1 tests remain green.

## Release closure requirements

The 0.7.2 gate follows the established EngCalc protocol: focused feature tests; complete source suite; version bump only in closing task; real wheel; clean virtual environment; outside-checkout smoke with `PYTHONPATH=''`; source-free installed-wheel full suite; repeated source suite; temporary workflow removal; authoritative `CURRENT.md` evidence.

## Explicitly out of scope for 0.7.2

- CSV/Excel/download/export APIs;
- pandas as a runtime dependency;
- editable or interactive spreadsheet tables;
- arbitrary table styling kwargs;
- cross-dimension response columns in one table;
- Cartesian multi-parameter table sweeps;
- named structural cases/combinations;
- exact extrema/roots/intersections;
- piecewise expressions;
- derivation traces;
- arbitrary Python list syntax.

## Intended next milestone

After 0.7.2 closes, the existing roadmap continues to 0.7.3 derivation traces unless a newly approved roadmap amendment changes that order.
