# EngCalc 0.9.1 — Exact-First Extrema, Roots and Intersections — Design

_Date: 2026-08-30_
_Status: conversational design approved; written specification pending user review before implementation planning_
_Active branch: `feature/v0.9.1-exact-characteristics`_
_Baseline: `main@cdc454db7ea43e57e334d523afded8b4ef498ded` (EngCalc 0.9.0 Matrix/CAS integrated)_

## 1. Purpose

EngCalc 0.9.1 introduces an exact-first characteristic-analysis layer for scalar engineering responses. The release separates authoritative extrema, roots and intersections from the 201-point sampling policy currently used to render plots.

The public operations are:

```text
extrema(M(x), x, 0, L)
roots(V(x), x, 0, L)
intersections(M_1(x), M_2(x), x, 0, L)
```

The mathematical result must be derived symbolically whenever SymPy can do so. Numerical search is a controlled fallback, never an implicit replacement for exact algebra and never tied to plot sampling density.

The same internal characteristic-analysis core will also become the reusable mathematical foundation for the later 0.9.2 exact-envelope/governing-interval release.

## 2. Baseline and invariants

EngCalc 0.9.1 starts from the integrated 0.9.0 baseline and must preserve all released behavior unless this specification explicitly extends it.

Regression invariants include:

- `%%eng` remains a restricted DSL rather than arbitrary Python/SymPy execution;
- symbolic expressions and Pint-backed numeric quantities remain distinct layers;
- `numeric(...)`, `result(...)`, tables, plots, envelopes, multi-argument functions, Piecewise, matrices and matrix indexing remain backward compatible;
- whole matrices remain invalid scalar responses while indexed scalar matrix expressions remain valid;
- positive structural moment continues to plot downward;
- existing plot sampling remains a rendering policy, not the authoritative characteristic-analysis method;
- no SciPy or other new runtime dependency is introduced.

## 3. Architectural decision

Characteristic mathematics will live in a dedicated internal module, expected to be `src/engcalc_colab/characteristics.py`.

This module owns:

- finite real-domain normalization;
- Piecewise domain partitioning;
- exact root solving;
- exact intersection solving;
- stationary-point solving;
- endpoint and Piecewise-boundary candidate generation;
- discontinuity-aware one-sided evaluation;
- exact-versus-numeric provenance;
- deterministic numerical fallback;
- de-duplication and stable ordering of characteristic locations;
- global/local extremum classification.

The parser remains responsible only for admitting the three public names and validating restricted syntax. The engine resolves symbolic responses, variable and domain and invokes the characteristic core. Renderers consume structured results and do not solve mathematics.

`plotting.py` must stop treating sampled `_extreme_indices(...)` values as authoritative characteristic coordinates when exact characteristic data is available. Sampling continues to draw curves.

## 4. Public API and statement contract

### 4.1 Supported forms

```text
extrema(response, variable, lower, upper)
roots(response, variable, lower, upper)
intersections(response_1, response_2, variable, lower, upper)
```

All arguments are positional. Keyword arguments are not introduced.

### 4.2 Standalone analysis statements

In 0.9.1 these operations are standalone analysis statements, analogous to `plot(...)` and `table(...)` in presentation behavior.

The following is supported:

```text
extrema(M(x), x, 0, L)
```

The following is intentionally rejected in 0.9.1:

```text
E = extrema(M(x), x, 0, L)
numeric(extrema(M(x), x, 0, L))
table(extrema(M(x), x, 0, L), x, 0, L, 11)
```

This avoids exposing internal structured result objects as ordinary symbolic values before a real compositional use case exists. The internal result models remain reusable by plot/envelope code.

### 4.3 Scalar-response requirement

Each response must resolve to one scalar symbolic expression.

Valid examples include:

```text
roots(V(x), x, 0, L)
extrema(K(x)[1,1], x, 0, L)
intersections(u(x)[1], v(x)[1], x, 0, L)
```

A whole matrix is rejected with an operation-specific diagnostic such as:

```text
extrema response must be scalar; index the matrix first, for example A[1,1]
```

No element-wise whole-matrix characteristic semantics are introduced.

## 5. Variable and domain semantics

### 5.1 Variable

The analysis variable argument must be a direct DSL name resolving to a symbolic scalar variable. Arbitrary expressions are not valid variable arguments.

### 5.2 Bounds

The lower and upper bounds define a closed finite real interval.

Requirements:

- both bounds must resolve numerically in the current Pint numeric context;
- their units must be mutually compatible;
- `lower < upper` after normalization;
- infinite, NaN, complex or unresolved bounds are rejected;
- a dimensionless variable requires dimensionless bounds;
- a dimensional variable may use compatible units on the two bounds, for example `0*m` and `600*cm`.

The engine normalizes the domain to one analysis scale while preserving the symbolic forms needed for exact substitution and display.

### 5.3 Variable-unit inference

EngCalc does not attach units directly to a SymPy symbol. The characteristic layer therefore infers the variable's numerical scale from the domain bounds and the existing numeric context, following the same unit-aware boundary used by table/plot evaluation.

A bare exact zero is permitted at a domain endpoint when the opposite bound supplies an unambiguous physical unit, consistent with EngCalc's dimensional-zero policy.

## 6. Exact-first solving strategy

Every operation follows the same hierarchy:

1. resolve and simplify the scalar symbolic problem without converting coefficients to floats unnecessarily;
2. partition Piecewise domains when required;
3. attempt exact real solving on each continuous region;
4. normalize and filter exact candidates to the requested closed domain;
5. validate candidates by substitution/domain membership rather than trusting solver output blindly;
6. only when an exact finite result cannot be obtained, invoke deterministic numerical fallback on the unresolved region;
7. mark every fallback-derived point as numerical/approximate.

The implementation may use SymPy `solveset`, `solve`, algebraic simplification and exact substitution. It must not expose raw SymPy `ConditionSet`/set implementation details directly to the user.

An exact solution remains exact internally even when a numerical quantity is also computed for display. For example, if `x = 5*L/8`, the result retains that symbolic location while also evaluating the corresponding Pint quantity when `L` is numeric.

## 7. Numerical fallback contract

### 7.1 When fallback is allowed

Fallback is permitted only when the exact solver cannot produce a finite usable solution set for a continuous subdomain.

It must not run merely because an exact result is algebraically complicated.

### 7.2 Independence from plotting

Fallback must not reuse the plot's 201-point grid as its authoritative answer.

A deterministic internal scan may be used to identify brackets or initial guesses, followed by SymPy/mpmath numerical root refinement. The scan density and refinement policy belong to the characteristic solver and are separately tested.

### 7.3 Validation

Every numerical root candidate must be:

- finite;
- real within tolerance;
- inside the target subdomain;
- residual-validated against the governing equation;
- de-duplicated against other exact/numeric candidates using a scale-aware tolerance.

Brackets separated by a discontinuity are never treated as continuous sign changes.

### 7.4 Provenance

Structured results distinguish at least:

- `exact` — obtained from exact symbolic reasoning;
- `numeric` — obtained through numerical fallback.

Renderers visibly mark approximate values, for example with `≈`, rather than presenting them as exact equalities.

## 8. `roots(...)` semantics

`roots(f(x), x, a, b)` solves `f(x) = 0` on the requested domain.

Required behavior:

- return only real roots in `[a,b]`;
- endpoints count as roots when the function is defined there and evaluates to zero;
- roots are ordered by increasing physical x coordinate;
- repeated algebraic roots appear once at the same location;
- an exact dimensional zero is accepted as the response zero without fabricating a unitless physical comparison;
- undefined points are never roots;
- a sign change across a Piecewise discontinuity is not a root unless the function is actually defined as zero at the breakpoint;
- exact roots and fallback roots may coexist in one result when different Piecewise regions require different solution methods.

### 8.1 Identically zero regions

If `f(x)` is identically zero on a nonzero-length interval, the root set is infinite rather than a finite point list.

The structured result records an infinite root interval and the renderer states that every point in that interval is a root. EngCalc must not fabricate an arbitrary finite set of sample roots.

If the complete requested domain is identically zero, the result reports the whole domain as the root interval.

## 9. `intersections(...)` semantics

`intersections(f(x), g(x), x, a, b)` solves `f(x) - g(x) = 0` on the requested domain.

Before solving numerically, the two responses must be dimensionally compatible over the evaluated domain. EngCalc must not silently compare force with moment, displacement with rotation, or otherwise incompatible physical dimensions.

Required behavior:

- exact solve of `f-g` is attempted first;
- only real in-domain intersections are retained;
- each returned point stores x plus both response values;
- response values must agree within exact equality or numerical tolerance after unit normalization;
- Piecewise discontinuities are respected independently for both responses;
- crossing by jump without equality at a defined point is not an intersection;
- coincident finite intervals are represented as coincident intervals, not as arbitrarily sampled points;
- isolated endpoint intersections are valid;
- output order is increasing x.

A later 0.9.2 envelope implementation will reuse this same intersection engine to partition governing intervals.

## 10. `extrema(...)` semantics

`extrema(f(x), x, a, b)` finds engineering characteristic extrema on the closed requested domain.

Candidate locations include:

1. stationary points inside continuous regions where `df/dx = 0`;
2. finite interval endpoints where the function is defined;
3. Piecewise breakpoints where the function is defined;
4. finite one-sided limiting values at Piecewise boundaries when the corresponding side belongs to the requested domain.

### 10.1 Classification

Each finite candidate may be classified as:

- local maximum;
- local minimum;
- global maximum;
- global minimum;
- both local/global when applicable;
- boundary candidate where one-sided topology prevents an ordinary interior classification.

Global extrema are determined by comparing all valid candidate values in a common compatible response scale, not by sampled plot magnitudes.

When exact ordering is decidable symbolically, exact comparison is preferred. When numeric context is required to order dimensionally meaningful candidates, the comparison uses normalized Pint quantities while preserving exact symbolic source values.

### 10.2 One-sided Piecewise values

At a discontinuity, the exact point value and finite left/right limiting values are distinct characteristic candidates when they differ.

The structured point therefore records a side discriminator:

- `at` — actual value at the x coordinate;
- `left` — limiting value as x approaches from the left;
- `right` — limiting value as x approaches from the right.

This is important for structural response diagrams with jump discontinuities such as shear across a point load.

### 10.3 Constant regions

A function constant over the complete requested interval has infinitely many maximizers and minimizers. The result records the domain interval as both a maximum and minimum locus rather than selecting an arbitrary endpoint.

A Piecewise function may similarly contain a constant subinterval that forms an extremum locus. Such loci are represented explicitly as intervals when they govern the global value.

### 10.4 Unbounded behavior

If the response is unbounded above or below on the requested domain because of a singularity or open-sided divergence inside a Piecewise/continuous region, EngCalc reports that direction as unbounded.

It must not report the largest sampled finite number as a maximum or minimum.

## 11. Piecewise and discontinuity architecture

Existing `extract_symbolic_breakpoints(...)` remains the canonical source for explicit direct Piecewise breakpoints where applicable.

The characteristic layer supplements those breakpoints with domain membership analysis and one-sided evaluation; it does not reparse Piecewise syntax independently.

For each Piecewise response, the requested interval is partitioned into mathematically continuous subdomains. For intersections, the union of breakpoints from both responses is used.

Each subdomain is solved independently. This prevents:

- false roots created by jumps;
- false intersections across discontinuities;
- numerical root bracketing through undefined regions;
- missed boundary extrema.

Nested or algebraically transformed Piecewise expressions are supported to the extent the existing symbolic expression exposes analyzable Piecewise structure. If a domain cannot be partitioned safely, EngCalc emits an explicit diagnostic rather than silently sampling across the ambiguity.

## 12. Structured result model

The exact class names may be refined during implementation planning, but the semantic fields are fixed by this design.

### 12.1 Characteristic point

A common immutable point model stores at minimum:

- symbolic x location;
- evaluated x quantity;
- symbolic response value where meaningful;
- evaluated response quantity where meaningful;
- provenance: `exact` or `numeric`;
- side: `at`, `left` or `right`;
- operation-specific role/classification;
- source response identity required for rendering and downstream plot/envelope use.

### 12.2 Characteristic interval

An immutable interval model represents infinite loci such as:

- identically-zero root intervals;
- coincident intersection intervals;
- constant extremum loci.

It stores lower/upper symbolic and evaluated bounds plus interval role/provenance.

### 12.3 Operation results

Dedicated immutable result containers represent:

- roots;
- intersections;
- extrema.

They preserve stable source order metadata and separate finite points, interval loci and status flags such as unbounded directions.

The renderer receives these typed results directly. Raw dictionaries or ad-hoc tuples are not the public internal contract.

## 13. Engine integration

The evaluator gains dedicated paths for the three whitelisted calls.

The engine must:

1. validate arity and direct-variable syntax;
2. resolve user functions, substitutions, indexed matrix scalars and Piecewise expressions through existing evaluator machinery;
3. reject whole matrices before characteristic solving;
4. resolve unit-aware domain bounds without mutating global symbols;
5. invoke the characteristic core;
6. produce one typed analysis result tied to the original `ParsedStatement`;
7. reject assignment/nesting forms specified as unsupported;
8. preserve line-numbered EngCalc diagnostics.

No arbitrary callable access to SymPy is added.

## 14. Plot integration

### 14.1 Authoritative extrema

For ordinary scalar and multi-series `plot(...)`, characteristic extrema displayed on the figure must come from the characteristic-analysis core rather than `_extreme_indices(...)` over the sampled y array.

Sampling still controls the visual polyline. Characteristic coordinates are mathematically independent of that sampling.

### 14.2 Plot-series model

`PlotSeries` or an adjacent typed plot metadata structure may be extended to carry authoritative characteristic points. The renderer consumes those points for markers/labels/summary panels.

The renderer must not independently call symbolic solvers.

### 14.3 Piecewise plots

For Piecewise plots, left/right characteristic points may share the same x coordinate. The renderer must preserve the mathematical distinction without altering existing segmented-curve behavior.

### 14.4 Envelope boundary

`envelope(...)` keeps its existing sampled governing-case mathematics in 0.9.1 except where it already consumes ordinary source-series rendering metadata.

Exact envelope crossovers and governing intervals remain explicitly deferred to 0.9.2. This release must not partially implement 0.9.2 semantics.

## 15. Rendering and presentation

Each standalone analysis renders an engineering-readable compact result rather than Python representations of dataclasses/SymPy sets.

### 15.1 Roots

Show the response identity, domain and ordered root locations. Exact roots use equality; numerical fallback roots use approximate equality.

Infinite root intervals are stated explicitly.

### 15.2 Intersections

Show ordered x coordinates and the common response value with units. Coincident intervals are identified explicitly.

### 15.3 Extrema

Show location, response value, classification and side where relevant. Global extrema must be visually distinguishable from merely local/boundary candidates without excessive decoration.

### 15.4 Units

Units are shown compactly and consistently with existing EngCalc formatting. Compatible values use a common display scale where practical. Exact symbolic forms are retained when informative, with evaluated engineering quantities shown alongside when the numeric context resolves them.

## 16. Diagnostics

Diagnostics must be concise, operation-specific and actionable.

Required error families include:

- wrong arity;
- invalid/non-name analysis variable;
- unresolved or non-finite domain bound;
- incompatible lower/upper units;
- reversed/zero-width domain;
- whole-matrix response;
- incompatible response dimensions for intersections;
- characteristic call used in unsupported assignment/nesting context;
- unsafe/unresolved Piecewise partition;
- numerical fallback unable to validate a candidate set;
- solver result that is not representable safely as finite points/intervals.

A solver limitation must never degrade silently into a sampled answer presented as exact.

## 17. Expected implementation boundaries

Expected primary files:

- `src/engcalc_colab/characteristics.py` — new mathematical core;
- `src/engcalc_colab/models.py` — typed characteristic point/interval/result models and plot metadata;
- `src/engcalc_colab/parser.py` — whitelist and syntax validation for three public calls;
- `src/engcalc_colab/engine.py` — resolution, unit/domain boundary and result integration;
- `src/engcalc_colab/plotting.py` — consume authoritative extrema rather than sampled extrema;
- presentation/renderer module(s) — render standalone characteristic results and updated plot metadata;
- focused new characteristic tests;
- focused plot regression tests;
- README/reference examples;
- `docs/project-context/CURRENT.md`.

`numeric.py`, `piecewise.py` and matrix modules should be reused rather than broadly refactored. Targeted helper additions are acceptable only where the characteristic core needs an existing responsibility exposed cleanly.

## 18. RED → GREEN TDD contract

Implementation must begin with failing tests before production behavior changes.

### 18.1 Parser/API RED tests

Cover:

- accepted canonical calls;
- wrong arity;
- unsupported keywords;
- invalid variable argument;
- assignment/nesting rejection;
- whole-matrix rejection and indexed-scalar acceptance.

### 18.2 Exact roots tests

At minimum:

- polynomial with rational exact roots;
- repeated root de-duplication;
- endpoint root;
- no real roots;
- dimensional engineering response with dimensional zero;
- Piecewise root in one branch;
- jump sign-change that is not a root;
- identically-zero complete domain;
- identically-zero subinterval.

### 18.3 Exact intersections tests

At minimum:

- two polynomial responses with exact intersections;
- endpoint intersection;
- incompatible response dimensions;
- no intersections;
- Piecewise intersection;
- jump crossing without equality;
- coincident complete/subinterval cases;
- indexed scalar matrix response.

### 18.4 Extrema tests

At minimum:

- quadratic interior exact maximum/minimum;
- endpoint-controlled global extremum;
- multiple local extrema;
- Piecewise breakpoint extremum;
- discontinuity with distinct `left`, `at`, `right` values;
- constant complete domain;
- constant governing subinterval;
- unbounded singular response;
- dimensional response and dimensional domain.

### 18.5 Numerical fallback tests

Use deliberately non-algebraic cases where exact finite solving is unavailable but numerical roots/extrema are stable.

Prove:

- fallback is invoked only after unresolved exact solving;
- approximate provenance is preserved;
- result is independent of the public plot 201-point grid;
- residual validation rejects false roots;
- discontinuities are not bracketed across;
- duplicate approximate roots collapse deterministically.

### 18.6 Plot integration tests

Construct a response whose true extremum lies between the current 201 plotting samples and prove:

- plotted line sampling remains unchanged;
- characteristic marker/label uses the exact location/value;
- multi-series plots receive per-series exact characteristics;
- Piecewise segment rendering remains correct;
- positive structural moment remains downward;
- existing dense/sparse characteristic-label presentation receives the authoritative points without changing its presentation contract.

### 18.7 Full regression

The complete 0.9.0 suite must remain green throughout implementation.

## 19. Documentation acceptance examples

README/reference documentation must include executable examples for:

1. beam-like moment extrema;
2. shear roots;
3. intersections between two response cases;

## 21. Explicit non-goals

0.9.1 does not include:

- exact governing intervals or exact envelope crossover replacement — 0.9.2;
- named response cases/combinations — 0.9.3;
- engineering `check(...)` verification — 0.10.x;
- generalized matrix eigenproblems;
- whole-matrix extrema/roots/intersections;
- multivariable optimization;
- unconstrained/infinite-domain optimization;
- inequality solving as a public API;
- arbitrary user tolerances/solver kwargs;
- SciPy dependency;
- symbolic proof traces;
- adaptive plotting as a substitute for exact characteristic analysis.

## 22. Acceptance criteria

The release design is satisfied only when all of the following are true:

- the three public standalone operations work through `%%eng` with typed results and engineering rendering;
- exact symbolic solving is authoritative whenever available;
- numerical fallback is deterministic, validated, visibly approximate and independent of plot sampling;
- units are preserved and incompatible dimensions are rejected rather than stripped;
- Piecewise discontinuities cannot create false roots/intersections and one-sided extrema are representable;
- infinite loci and unbounded behavior are represented explicitly rather than sampled into arbitrary points;
- whole matrices are rejected while indexed scalar matrix responses work;
- ordinary and multi-series plots use authoritative characteristic extrema while retaining their existing rendering/sampling behavior;
- envelope exactness remains deferred to 0.9.2;
- focused and full regression suites pass;
- real-wheel/source-free validation passes at release closure;
- no temporary validation workflow remains;
- no merge occurs without explicit user approval.
