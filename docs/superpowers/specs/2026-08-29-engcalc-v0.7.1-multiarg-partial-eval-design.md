# EngCalc 0.7.1 — Multi-Argument Functions and Generalized Partial Evaluation

## Status

Design specification for EngCalc **0.7.1**. This milestone starts from merged and validated EngCalc 0.7.0 on `main` and implements the roadmap milestone **multi-argument user functions and generalized partial evaluation**.

This document freezes behavior before implementation. No production-code change belongs to 0.7.1 until this design is approved and an implementation plan is written.

## Goal

EngCalc 0.7.1 removes the one-argument limitation of user-defined functions without making ordinary engineering calculations more verbose.

The core mental model is:

> Parameters written inside a function signature are the values the author wants to pass explicitly on each call. Symbols not listed as parameters may continue to come from the surrounding EngCalc context.

Therefore 0.7.1 **adds parametrization; it does not require it**.

Both of these are first-class styles:

```text
# Simple/context-driven style
M(x) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

# Reusable/explicitly parametrized style
M_base(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
```

The first keeps `q` and `L` in the EngCalc context. The second makes `q` and `L` explicit inputs. Neither style is globally preferred; users choose the amount of parametrization that improves readability and reuse for a given calculation.

## Baseline preserved from 0.7.0

0.7.1 must preserve all public 0.7.0 behavior, including:

- one-argument functions such as `M(x) = ...`;
- numeric assignments with `:=` and Pint units;
- `numeric(...)` and `result(...)`;
- direct unit-bearing function arguments, including dimensional zero;
- scalar engineering math `sqrt`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `exp`, `log`, and `pi`;
- inverse-trig angle semantics and explicit `rad` / `deg` rendering;
- plotting, multi-series plotting, one-parameter sweeps and envelopes;
- the 201-point rendering grid;
- structural positive moment plotted downward;
- existing parser safety restrictions and no arbitrary Python/SymPy execution.

## 1. Function-definition syntax

### 1.1 One parameter remains unchanged

```text
M(x) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
```

This remains the normal concise style when only `x` needs to vary explicitly.

### 1.2 Two or more parameters

```text
qU(qD, qL) = 1.2*qD + 1.6*qL

M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

sigma(M, y, I) = M*y/I
```

A user function has **one or more positional named parameters**.

### 1.3 Partially parametrized functions

A formula may mix explicit parameters and context/global symbols:

```text
M(x, q) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
L := 4*m
```

Here `x` and `q` are explicit inputs while `L` comes from the surrounding EngCalc context.

This is intentional and supported.

### 1.4 Unused parameters are legal

```text
f(x) = 5
```

is a valid constant function. EngCalc does not reject an unused parameter merely because the body is independent of it.

Documentation should avoid unnecessary parameters when they reduce clarity. For example, prefer:

```text
qU(qD, qL) = 1.2*qD + 1.6*qL
```

over the unnecessarily verbose:

```text
qU(x, qD, qL) = 1.2*qD + 1.6*qL
```

## 2. Parameter rules

Function parameters must satisfy all of the following:

1. at least one parameter;
2. positional only;
3. valid EngCalc identifiers;
4. unique within the signature;
5. not Python keywords;
6. not EngCalc reserved names such as `numeric`, `plot`, `sin`, `pi`, etc.;
7. no default values;
8. no `*args` or `**kwargs`;
9. no keyword-only syntax.

Examples:

```text
M(x, q, L) = ...      # valid
M(x, q, q) = ...      # error: duplicate parameter q
f(x, sin) = ...       # error: reserved parameter sin
f(pi, x) = ...        # error: reserved parameter pi
f() = ...             # error: user functions require at least one parameter
```

## 3. Function names and overloading

EngCalc 0.7.1 does **not** add function overloading by arity.

There is only one active user-function definition for a given name.

Therefore EngCalc does not maintain separate simultaneous meanings for:

```text
M(x) = ...
M(x, q, L) = ...
```

A later redefinition of an existing function name replaces the previous active function definition, preserving the existing EngCalc redefinition model; calls are checked against the currently active signature only.

When both a generic and a specialized form are useful, use distinct names:

```text
M_base(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
M_U(x) = M_base(x, 1.2*qD + 1.6*qL, L)
```

0.7.1 does not introduce recursive-function semantics. Calculations should use distinct generic and specialized function names rather than patterns such as `M(x) = M(x, ...)`.

## 4. Local parameters versus context/global symbols

### 4.1 Parameters are local to the function body

Parameters shadow same-named context values while the function body is interpreted.

For example:

```text
L := 5*m
f(L) = 2*L
numeric(f(3*m))
```

The `L` inside `f(L)` is the local function parameter. The call evaluates with `L = 3*m`, not the context value `5*m`.

### 4.2 Context symbols remain available when they are not parameters

```text
M(x) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
q := 10*kN/m
L := 4*m
```

Here `q` and `L` remain context values. A caller supplies only `x`:

```text
numeric(M(2*m))
```

### 4.3 A context value may be passed into a local parameter

```text
L := 5*m
qD := 4*kN/m
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

numeric(M(2*m, qD, L))
```

The caller-side `qD` and `L` resolve from the context and are then bound positionally to the local parameters `q` and `L`.

### 4.4 Existing EngCalc name resolution remains authoritative

0.7.1 changes only the handling of **local function parameters**. Names that are not parameters continue to follow EngCalc's existing name-resolution behavior.

In particular:

- symbolic assignments made with `=` keep their existing symbolic namespace/capture semantics;
- numeric assignments made with `:=` remain in the separate Pint-backed numeric context and do not mutate stored symbolic formulas;
- during `numeric(...)`, `result(...)` and numeric plot sampling, known `:=` values are used to substitute remaining symbols when appropriate;
- this release does not introduce a new closure model, dynamic-global lookup model or snapshot rule for symbols outside the parameter list.

The implementation must therefore avoid changing existing 0.7.0 behavior for context-driven functions such as `M(x) = ...`; it only adds ordered local parameter binding for signatures with one or more arguments.

## 5. Exact positional arity

Every user-function call must provide exactly as many positional arguments as the active definition declares.

For:

```text
M(x, q, L) = ...
```

these rules apply:

```text
M(x)             # error
M(x, q)          # error
M(x, q, L)       # valid
M(x, q, L, E)    # error
```

The diagnostic should identify the function, expected count/signature and received count, for example:

```text
function 'M' expects 3 arguments (x, q, L), received 2
```

Keyword arguments remain unsupported:

```text
M(x=x0, q=qD, L=L)   # error
```

## 6. Symbolic calls

Multi-argument user functions work as normal symbolic expressions.

```text
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
M_D(x) = M(x, qD, L)
M_U(x) = M(x, 1.2*qD + 1.6*qL, L)
```

The engine binds arguments to parameters positionally and substitutes the function body symbolically.

Nested/composed user functions are supported:

```text
qU(qD, qL) = 1.2*qD + 1.6*qL
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
M_U(x) = M(x, qU(qD, qL), L)
```

This makes it possible to separate calculation responsibilities:

```text
qD, qL -> qU(qD,qL) -> M(x,q,L) -> M_U(x)
```

## 7. Numeric calls — fully known arguments

When all function arguments and all required context symbols are numerically known, `numeric(...)` / `result(...)` produce a normal fully numeric Pint result.

```text
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

numeric(M(2*m, 10*kN/m, 4*m), kN*m)
```

Equivalent context-backed form:

```text
qD := 10*kN/m
L := 4*m
numeric(M(2*m, qD, L), kN*m)
```

Arguments may themselves be complete numeric expressions:

```text
qD := 4*kN/m
qL := 2*kN/m
L := 5*m

numeric(M(2*m, 1.2*qD + 1.6*qL, L), kN*m)
```

Each argument is resolved independently through the restricted Pint-backed numeric context before it is bound to its corresponding parameter.

The dimensional-zero guarantee from 0.6.2 applies to every argument, not only the first:

```text
numeric(f(0*m, 4*kN/m, 5*m))
```

must not lose the dimension carried by `0*m`.

## 8. Generalized partial numeric evaluation

### 8.1 Principle

`numeric(...)` substitutes **everything EngCalc knows numerically** and preserves **everything still intentionally symbolic**.

This behavior is no longer limited to a one-argument polynomial function.

### 8.2 One unresolved parameter

```text
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
qD := 10*kN/m
L := 4*m

numeric(M(x, qD, L))
```

Expected semantic result:

- `qD` is substituted numerically;
- `L` is substituted numerically;
- `x` remains symbolic;
- no final target-unit conversion is attempted because the result is not fully numeric.

### 8.3 Multiple unresolved parameters

```text
L := 4*m
numeric(M(x, q, L))
```

Expected semantic result:

- `L` is substituted;
- `x` remains symbolic;
- `q` remains symbolic.

EngCalc must not fail merely because more than one symbol remains unresolved.

### 8.4 Known context symbols inside the function body are also substituted

```text
M(x, q) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
L := 4*m
qD := 10*kN/m

numeric(M(x, qD))
```

Both the explicit argument `qD` and context symbol `L` are known and substituted; `x` remains symbolic.

### 8.5 Generalized non-polynomial partial evaluation

0.7.1 extends partial evaluation to scalar-math expressions from 0.7.0:

```text
v(x, A, L) = A*sin(pi*x/L)
A := 20*mm
L := 4*m

numeric(v(x, A, L))
```

The result preserves the structure equivalent to:

```text
20*mm*sin(pi*x/(4*m))
```

with `x` unresolved.

The same principle applies to supported compositions involving `sqrt`, trigonometric functions, inverse trigonometric functions, `exp`, and `log`, subject to the existing 0.7.0 dimensional rules whenever enough information is available to evaluate them safely.

### 8.6 No fabricated final unit

A partially evaluated expression has no fabricated overall Pint unit merely because some known substitutions carry units.

The renderer may show units on known substituted quantities, but if unresolved symbols prevent a fully numeric dimensional result, EngCalc preserves the symbolic expression rather than inventing a final result unit.

### 8.7 Target-unit conversion requires a fully numeric result

The existing rule remains:

```text
numeric(M(x, qD, L), kN*m)
```

is an error if `x` remains unresolved.

The diagnostic should state that target-unit conversion requires a fully numeric result and identify unresolved symbols when possible.

## 9. Partial-evaluation presentation

The presentation goal is:

1. original formula/call;
2. known substitutions;
3. remaining symbolic expression.

For polynomial expressions, EngCalc may keep the richer existing evaluated-term rendering when it is valid.

For non-polynomial/general expressions, 0.7.1 introduces a general structural fallback instead of forcing the expression through the polynomial-only term evaluator.

Example source:

```text
v(x, A, L) = A*sin(pi*x/L)
A := 20*mm
L := 4*m
numeric(v(x, A, L))
```

Conceptual presentation:

```text
v(x, A, L) = A sin(pi x / L)
A = 20 mm, L = 4 m
v(x) = 20 mm sin(pi x / (4 m))
```

Exact MathJax layout remains a renderer concern; the semantic contract is that known substitutions and remaining symbolic dependencies are visible and truthful.

## 10. Unit semantics

0.7.1 does not add unit declarations to function signatures. Units continue to belong to numerical values, not to parameter declarations.

```text
sigma(M, y, I) = M*y/I
```

does not declare the dimensions of `M`, `y`, or `I`. Pint validates dimensional compatibility during numeric evaluation.

All 0.7.0 scalar-function unit rules remain authoritative:

- `sqrt` propagates dimensions through a half-power;
- forward trig accepts dimensionless values or angle quantities;
- inverse trig requires truly unitless inputs and returns radians;
- `exp` / `log` require truly unitless inputs;
- explicit `deg` / `rad` remain rejected by dimensionless-only functions;
- explicit angle units remain visible in rendering.

Incompatible operations inside a multi-argument user function must raise the same engineering-facing errors used by the existing numeric engine, with the function name/signature included when it improves diagnosis.

## 11. Plotting and envelopes

Multi-argument functions must compose with existing response plotting without adding a new plotting language.

Direct example:

```text
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
qD := 4*kN/m
L := 5*m

plot(M(x, qD, L), x, 0*m, L)
```

Specialized-function example:

```text
M_D(x) = M(x, qD, L)
plot(M_D(x), x, 0*m, L)
```

Existing multi-series/envelope forms remain valid when their response expressions contain multi-argument user-function calls:

```text
M_U(x) = M(x, 1.2*qD + 1.6*qL, L)
envelope(M_D(x), M_U(x), x, 0*m, L)
```

0.7.1 does **not** add Cartesian multi-parameter plot sweeps. The existing one-parameter sweep capability remains the limit.

## 12. Engineering composition examples

### 12.1 Context-driven workflow

```text
M(x) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
q := 10*kN/m
L := 4*m

numeric(M(x))
numeric(M(2*m), kN*m)
plot(M(x), x, 0*m, L)
```

### 12.2 Fully parametrized reusable formula

```text
M_base(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

qD := 4*kN/m
qL := 2*kN/m
L := 5*m

numeric(M_base(x, qD, L))
numeric(M_base(2*m, 1.2*qD + 1.6*qL, L), kN*m)
```

### 12.3 Specialized response cases

```text
M_base(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2

M_D(x) = M_base(x, qD, L)
M_L(x) = M_base(x, qL, L)
M_U(x) = M_base(x, 1.2*qD + 1.6*qL, L)
```

### 12.4 Separate load-combination function

```text
qU(qD, qL) = 1.2*qD + 1.6*qL
M_base(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
M_U(x) = M_base(x, qU(qD, qL), L)
```

### 12.5 Chained engineering formulas

```text
qU(qD, qL) = 1.2*qD + 1.6*qL
M(x, q, L) = -q*L^2/8 + 5*q*L*x/8 - q*x^2/2
sigma(M, y, I) = M*y/I

M_U(x) = M(x, qU(qD, qL), L)
sigma_U(x) = sigma(M_U(x), y, I)
```

The intent is modular calculation: each reusable formula has a clear signature, while specialized engineering cases can reduce the number of inputs exposed to later calculations.

## 13. Error contracts

0.7.1 must provide stable, engineering-facing errors for at least:

- malformed multi-argument function target;
- zero parameters;
- duplicate parameters;
- reserved parameters;
- exact arity mismatch;
- keyword/default/variadic syntax;
- unresolved symbols when a fully numeric result is required;
- target-unit conversion of a partial result;
- incompatible units during multi-argument numerical evaluation;
- unsupported symbolic/numeric crossings.

Errors must preserve line numbers and the existing EngCalc public exception hierarchy.

Where safe, diagnostics should include the active function signature, for example:

```text
function 'M' expects 3 arguments (x, q, L), received 2
```

## 14. Internal architecture direction

The implementation should remove single-parameter assumptions rather than layering a separate multi-argument path beside them.

Expected architectural direction:

- `ParsedStatement`: ordered parameter tuple rather than a singular parameter field;
- `UserFunction`: ordered parameter tuple rather than a singular parameter field;
- one central positional argument binder for symbolic, numeric and plotting paths;
- one centralized partial-evaluation path that can represent zero, one or many unresolved symbols;
- preserve the polynomial-specific evaluated-term renderer as an optimization/presentation specialization, not as the general partial-evaluation engine;
- retain special inverse-trig reconstruction semantics introduced in 0.7.0 when substitutions rebuild user-function expressions;
- preserve direct AST-to-Pint argument resolution so dimensional zero is not erased by SymPy.

Compatibility helpers/properties may be used internally during migration, but production behavior must converge on one multi-argument model rather than permanent one-argument and multi-argument implementations.

## 15. Acceptance contract

0.7.1 is not complete until automated tests cover at minimum:

### Parser / model

```text
f(x) = x
f(x, a) = a*x
M(x, q, L) = ...
sigma(M, y, I) = M*y/I
```

plus duplicate/reserved/zero-parameter rejection, and a redefinition regression proving that one function name has only one active signature (the latest definition) rather than overload dispatch.

### Symbolic engine

- one-argument behavior unchanged;
- exact positional substitution for 2+ arguments;
- partial parametrization with context/global symbols;
- local parameter names shadow same-named context values;
- existing name-resolution/capture behavior for non-parameter symbols remains unchanged;
- nested user-function composition;
- scalar-math composition;
- exact arity diagnostics.

### Numeric engine

- all arguments fully numeric;
- numeric names used as arguments;
- complete numeric expressions used as arguments;
- dimensional zero in any argument position;
- incompatible units produce controlled errors;
- target conversion works for fully numeric results.

### General partial evaluation

- one unresolved parameter;
- multiple unresolved parameters;
- unresolved globals plus parameters;
- known globals substituted while unresolved symbols remain;
- polynomial partial evaluation remains correct;
- `A*sin(pi*x/L)` partial evaluation works;
- supported scalar-math compositions do not require polynomial form;
- partial results do not fabricate final units;
- target conversion rejects partial results.

### Plot / magic acceptance

At least one real `%%eng` acceptance cell must combine:

```text
M(x, q, L) = ...
qD := ...
L := ...
numeric(M(x, qD, L))
numeric(M(2*m, qD, L), kN*m)
plot(M(x, qD, L), x, 0*m, L)
```

and one acceptance cell must exercise a non-polynomial partial function such as:

```text
v(x, A, L) = A*sin(pi*x/L)
```

### Regression / distribution

- complete existing source suite remains green;
- package/runtime versions are bumped only at release closure;
- actual 0.7.1 wheel is built;
- wheel installs into a clean environment;
- smoke runs outside the repository source tree;
- full suite runs against the installed wheel with source path excluded;
- complete source suite is repeated;
- temporary validation workflow is removed before merge.

## 16. Explicitly out of scope for 0.7.1

- default parameter values;
- keyword arguments for user functions;
- variadic functions;
- function overloading by arity;
- recursion as a public user-function feature;
- function-signature unit declarations;
- Cartesian multi-parameter plot/envelope sweeps;
- tables (`0.7.2`);
- derivation traces (`0.7.3`);
- named structural cases (`0.8.3`);
- arbitrary Python execution or arbitrary SymPy function access.

## 17. Design decision summary

0.7.1 adopts a single general user-function model with ordered positional parameters.

The user remains free to choose among:

```text
M(x) = ...
M(x, q) = ...
M(x, q, L) = ...
```

according to which values should be explicit inputs. Symbols omitted from the signature may continue to come from the EngCalc context under the existing name-resolution rules.

Multi-argument functions are intended primarily to make reusable engineering formulas and composition easier, for example:

```text
qU(qD, qL)
M_base(x, q, L)
sigma(M, y, I)
```

while concise specialized functions remain natural:

```text
M_D(x)
M_L(x)
M_U(x)
sigma_U(x)
```

Generalized partial evaluation follows one rule: **substitute every value known numerically and preserve every unresolved dependency symbolically, without fabricating units or forcing polynomial form.**
