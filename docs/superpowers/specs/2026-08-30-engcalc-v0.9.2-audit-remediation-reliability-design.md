# EngCalc 0.9.2 — Audit Remediation & Reliability Design

## Status

Proposed design for user review.

## Baseline

- Canonical base: `main@698696bb8854fa197851cdbb2f5e4c08ef22178b`.
- Released baseline: EngCalc 0.9.1 Exact Characteristics.
- 0.9.1 post-merge source suite: **846/846 PASS**.
- External audit basis: independent Claude audit of `main@698696bb`, Python 3.14.3, 846/846 existing tests plus 38 adversarial probes.
- Active development branch: `feature/v0.9.2-audit-reliability`.
- Package/runtime version remains **0.9.1** until the release task.

## Motivation

The 0.9.1 audit found a silent correctness defect in characteristic root/intersection solving, a high-severity symbolic-domain defect, several consistency/model defects, and infrastructure gaps. The silent correctness defect violates the released exact-first/fallback contract because valid real roots can be reported as an empty result instead of activating deterministic numeric fallback.

0.9.2 therefore becomes a reliability/stabilization release. Exact envelopes are deferred until this foundation is corrected and decomposed.

## Release objective

0.9.2 must:

1. make `roots()` and `intersections()` complete and non-silent when SymPy exact solving is partial or returns exact objects EngCalc cannot directly evaluate;
2. make user engineering symbols explicitly real without breaking identity-sensitive code;
3. make unit literals consistent in bounds/domains;
4. normalize Piecewise symbolic boundary values and side topology;
5. close the confirmed low-severity renderer/plot/diagnostic defects;
6. establish permanent CI over the declared Python support range;
7. declare the notebook runtime dependency correctly;
8. investigate, but not speculate-fix, the audit’s unconfirmed risks;
9. split the monolithic characteristic solver only after corrected behavior is GREEN.

## Design principles

1. **External audit findings are leads, not authority.** Every confirmed audit defect gets an independent EngCalc RED test before production changes.
2. **No silent false negatives.** “Could not evaluate/validate this plausible candidate” must never become “there is no solution.”
3. **Exact-first remains the contract.** Numeric fallback supplements incomplete exact discovery; it does not replace valid exact results.
4. **Exact provenance wins.** If exact and numeric candidates deduplicate to the same physical point, retain the exact point.
5. **Engineering variables are real.** User-created symbolic variables represent real engineering quantities in 0.9.2.
6. **Piecewise topology is semantic.** `left`/`at`/`right` appear only when the value/topology distinction is mathematically meaningful.
7. **Units are first-class.** Adaptable zero inherits physical units consistently.
8. **Correct before refactor.** C/H/M fixes reach GREEN before module decomposition.
9. **No speculative product changes.** Potential risks require a reproducible failure first.
10. **Preserve 0.9.1 behavior.** All released features remain regression requirements, including positive structural moment plotted downward.

## Scope

### In scope

- **C-1:** exact-candidate evaluation plus completeness/fallback for roots and intersections.
- **H-1:** `real=True` symbol contract plus audit of every identity-sensitive symbol recreation.

- **I-1:** permanent GitHub Actions CI.
- **I-2:** declare IPython in project metadata.

- Investigation-only probes for residual tolerance, tri-state `is_real`, and expensive `sp.simplify` paths.

# C-1 — complete and safe roots/intersections

## Required RED reproductions

Before any C-1 product change, EngCalc’s own tests must reproduce:

```text
f(x) = log(x) - 1
roots(f(x), x, 1, 10)
# expected x = E ≈ 2.718281828...

g(x) = exp(x) - 3*x
roots(g(x), x, 0, 3)
# expected ≈ 0.6190612867 and 1.5121345517

h(x) = x^5 - x - 1
roots(h(x), x, 0, 2)
# expected ≈ 1.167303978...

intersections(log(x), 1 + 0*x, x, 1, 10)
# expected x = E
```

Also cover `E`, real `LambertW`, real `CRootOf`, exact/numeric merge, exact provenance preservation, close distinct roots, and a case where a plausible exact candidate cannot be evaluated.

## Closed SymPy numeric evaluation

`NumericContext._evaluate_sympy()` must accept a **closed, symbol-free, real, finite SymPy numeric expression** even when its concrete class is not hand-dispatched. This provides a numeric quantity for validation of exact objects such as `E`, real `LambertW(...)` and real `CRootOf(...)`.

The symbolic model is not degraded: `x_symbolic` and `value_symbolic` retain their exact SymPy objects. Non-real/non-finite closed expressions remain invalid in real engineering evaluation.

## Exact-discovery completeness

Exact discovery distinguishes **candidates** from **proof of completeness**:

- `solveset(..., domain=S.Reals) -> EmptySet` is authoritative: no roots.
- `solveset(...) -> FiniteSet` is authoritative for that finite real solution set.
- `solveset(...) -> S.Reals` is authoritative for an identically-zero topology.
- Any unresolved `solveset` result may fall back to `sp.solve(...)` for useful exact candidates.
- Results from `sp.solve(...)` are **candidate hints, not proof of completeness**.
- Therefore, whenever `sp.solve(...)` is used after unresolved `solveset`, the operation remains `needs_fallback=True` even if `solve` returns candidates.
- Deterministic numeric fallback runs over the physical domain and its results merge with validated exact candidates.

This rule is required to recover both real roots of `exp(x)-3*x` when symbolic solving exposes fewer branches.

## Candidate validation outcomes

Candidate processing must distinguish at least:

- accepted;
- provably non-real;
- outside domain;
- dimensionally incompatible;
- residual-invalid;
- evaluation unresolved/internal failure.

An internal `EngEvaluationError` while evaluating a plausible exact candidate is **not** evidence of nonexistence. It forces fallback/incomplete handling. If plausible candidates were lost to evaluation failures and fallback cannot establish a trustworthy result, raise an actionable `EngEvaluationError`; never return a confident empty set.

## Merge/dedup semantics

- Merge exact and numeric results in physical x order.
- Use domain-aware deduplication tolerances.
- When exact and numeric results coincide, retain the exact point/provenance.
- Preserve close distinct roots such as `(x-1)*(x-1.0000001)`.

## Shared intersections semantics

`intersections(f,g,...)` still solves the zero set of `f-g`, but it must reuse the same zero-set candidate discovery, validation, fallback and merge policy as `roots()`. There must not be a separate completeness policy.

# H-1 — real engineering symbols

## Symbol contract

`EngineeringEngine.resolve_symbol(name)` creates `sp.Symbol(name, real=True)`.

Independent variables, scalar symbolic names and function parameters resolved through the engine follow this rule. Complex engineering variables remain out of scope.

## Identity audit

Changing assumptions changes SymPy symbol identity. Before the product patch, search all source construction of symbols from strings. Any code referring to an existing expression variable must reuse the expression/engine symbol or construct it with the same assumptions.

This explicitly includes polynomial/partial-evaluation code that currently recreates `sp.Symbol(variable)` rather than reusing the actual free symbol.

## Required behavior

```text
u(x) = abs(x - 2)
extrema(u(x), x, 0, 4)
```

must return a global minimum at `x=2`, value `0`, without leaking `re(...)`, `im(...)`, `Derivative(...)` or internal Piecewise errors.

Also require a dimensional `extrema(abs(M(x)), ...)` case where `M` changes sign and broad regression coverage for substitutions, polynomial partial evaluation, Piecewise, matrix/CAS, differentiation, plots and tables.

---

# M-1 — unit literals in bounds

Known EngCalc unit aliases are valid directly in any supported numeric bound/domain:

```text
roots(V(x), x, 0*m, 6*m)
extrema(M(x), x, 0*m, 6000*mm)
intersections(M1(x), M2(x), x, 0*m, 6*m)
plot(M(x), x, 0*m, 6*m)
table(M(x), x, 0*m, 6*m, 5)
```

Explicit overrides and stored numeric values take precedence over interpreting a name as a unit alias, matching current characteristic-expression precedence.

Compatible units normalize to one physical domain. Incompatible dimensions remain errors.

Unit-literal resolution becomes a shared NumericContext/domain helper rather than characteristic-only duplicated logic.

---

# M-2 — selected Piecewise symbolic boundary value

For a numerically decidable Piecewise condition, extrema boundary `value_symbolic` is the exact expression of the governing branch, not an unresolved outer `Piecewise`.

Example:

```text
a := 3*m
L := 6*m
g(x) = piecewise(x-a, x<a, 2*(x-a))
extrema(g(x), x, 0, L)
```

Required:

- at `x=0`: `value_symbolic = -a`, numeric `-3 m`;
- at `x=L`: `value_symbolic` is `2*(L-a)` or mathematically equivalent, numeric `6 m`.

Branch selection may use numeric context, but symbolic output keeps user parameters symbolic.

---

# M-3 — Piecewise continuity and side topology

At an internal breakpoint:

- if left limit = explicit point value = right limit after unit normalization, emit exactly one `side="at"` point;
- if left/right differ, preserve one-sided values required by the existing discontinuity contract;
- if the explicit point value differs from one or both side limits, retain the distinct `at` value plus each meaningful distinct side value.

Dimensionless exact zero adapts to the response’s physical unit before comparisons/result construction. The same physical zero may not be dimensional in one record and dimensionless in another at the same point.

Existing discontinuous Piecewise interval openness and side semantics remain unchanged.

# L-1…L-4 — low-severity cleanup

## L-1 renderer contract

`render_result()` is a LaTeX renderer for calculation results; `render_characteristic_result()` is an HTML/MathJax renderer for characteristic results. 0.9.2 **does not merge these return contracts**.

If `render_result()` receives `RootsResult`, `IntersectionsResult` or `ExtremaResult`, it must raise an explicit `TypeError` (or EngCalc renderer-domain error if an existing suitable type exists) with guidance equivalent to:

```text
render_result does not support characteristic results; use render_characteristic_result
```

The current accidental `AttributeError` is prohibited. `%eng`/`%%eng` continues using `render_characteristic_result()` and is unchanged.

## L-2 font weight

Replace matplotlib `fontweight="semibold"` with numeric weight `600`. No intentional visual redesign.

## L-3 diagnostics

Piecewise missing-value/unit-literal diagnostics identify the missing symbol and provide the same actionable definition guidance as scalar numeric evaluation. Internal partitioning context may be appended, not substituted for user guidance.

## L-4 formatting

- Magnitudes within `RenderSettings.zero_tolerance` render as positive zero.
- Exact characteristic plot markers still use exact physical coordinates.
- For an exact compact coordinate such as `1/3`, the annotation displays the exact symbolic coordinate (and may include the configured numeric value in parentheses). It must not present `0.33` alone as though that were the authoritative location.
- Numeric-fallback coordinates continue using approximate notation.

## Permanent CI

Add and retain `.github/workflows/ci.yml` with:

- triggers: pull requests and pushes to `main`;
- matrix: Python 3.10, 3.11, 3.12, 3.13, 3.14;
- install: `python -m pip install -e '.[dev]'`;
- `python -m compileall -q src/engcalc_colab`;
- complete `python -m pytest -q`.

This workflow remains in the repository after release. Release-only validation workflows remain temporary and are cleaned up.

## IPython dependency

Because the primary notebook magic imports IPython directly, add IPython to declared runtime dependencies with a lower bound compatible with Python 3.10–3.14. CI must prove that a normal `.[dev]` install supplies the notebook runtime without a separate ad-hoc `pip install ipython` command.

## Python support

Keep:

```toml
requires-python = ">=3.10"
```

A failure on an advertised Python version is a compatibility bug to fix within 0.9.2. Narrowing the Python range requires separate explicit user approval and is not authorized here.

# Potential risks — investigation only

The audit did not reproduce failures for:

1. exact `float(magnitude) == 0.0` residual checks instead of configured tolerance;
2. `candidate.is_real is None` tri-state handling;
3. unbounded `sp.simplify` cost on large candidate expressions.

Add controlled tests/probes. Do **not** change product behavior unless a deterministic failing case is reproduced. Any newly reproduced failure becomes a normal RED→GREEN defect and is recorded in `CURRENT.md`.

# Characteristic solver decomposition

## Timing

Only after C-1, H-1, M-1, M-2 and M-3 are GREEN and the complete source suite passes.

## Required package layout

Replace `src/engcalc_colab/characteristics.py` with:

```text
src/engcalc_colab/characteristics/
    __init__.py
    domain.py
    candidates.py
    fallback.py
    roots.py
    intersections.py
    extrema.py
    piecewise_analysis.py
```

Responsibilities:

- `__init__.py`: stable public exports only.
- `domain.py`: `AnalysisDomain`, continuous-region/domain normalization, characteristic-domain unit handling.
- `candidates.py`: exact-discovery outcome, candidate validation outcome, ordering/deduplication, exact/numeric merge.
- `fallback.py`: deterministic numeric root/extrema scanning, refinement and residual validation.
- `roots.py`: root topology and public `solve_roots_exact`.
- `intersections.py`: dimensional compatibility and public `solve_intersections_exact`, reusing roots/zero-set semantics.
- `extrema.py`: stationary/boundary/local/global extrema logic and public `solve_extrema_exact`.
- `piecewise_analysis.py`: Piecewise partitioning, side limits, continuity and topology helpers.

The stable import remains:

```python
from engcalc_colab.characteristics import (
    normalize_analysis_domain,
    solve_roots_exact,
    solve_intersections_exact,
    solve_extrema_exact,
)
```

No public model/schema changes are made merely to enable the split.
