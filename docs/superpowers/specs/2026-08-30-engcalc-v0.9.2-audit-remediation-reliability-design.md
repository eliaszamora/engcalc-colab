# EngCalc 0.9.2 — Audit Remediation & Reliability Design

## Status

Proposed design for user review.

## Baseline

- Canonical base: `main@698696bb8854fa197851cdbb2f5e4c08ef22178b`.
- Released baseline: EngCalc 0.9.1 Exact Characteristics.
- 0.9.1 post-merge source suite: 846/846 PASS.
- External audit basis: independent Claude audit of `main@698696bb`, Python 3.14.3, 846/846 existing tests plus 38 adversarial probes.
- Active development branch: `feature/v0.9.2-audit-reliability`.
- Package/runtime version stays **0.9.1** until the release task.

## Motivation

The 0.9.1 audit found one silent correctness defect in characteristic root/intersection solving, one high-severity symbolic-domain defect, several consistency/model defects, and infrastructure gaps. The silent correctness defect violates the released 0.9.1 contract because valid real roots can be reported as an empty result instead of activating deterministic numeric fallback.

0.9.2 therefore becomes a reliability/stabilization release. The previously planned exact-envelope work is deferred until this foundation is corrected and simplified.

## Release objective

EngCalc 0.9.2 must make characteristic analysis trustworthy when SymPy exact solving is incomplete or returns exact objects that EngCalc cannot directly evaluate numerically, make user symbols explicitly real without breaking symbol identity elsewhere, normalize Piecewise boundary semantics, make unit literals consistent across domain-bearing APIs, close small rendering/diagnostic defects, establish permanent CI across the declared Python support range, and reduce duplicated characteristic-solver infrastructure before exact envelopes are added.

## Design principles

1. **External audit findings are leads, not authority.** Every confirmed audit defect must first be independently reproduced on the EngCalc branch with a RED regression test before production code changes.
2. **No silent false negatives.** An internal failure to evaluate or validate a mathematically plausible exact candidate must never be indistinguishable from “there is no solution.”
3. **Exact-first remains the contract.** Exact candidates are retained when valid. Numeric fallback supplements incomplete exact discovery; it does not replace valid exact results.
4. **Exact provenance wins.** If an exact and numeric candidate deduplicate to the same physical point, the final point remains `provenance="exact"`.
5. **Engineering variables are real.** User-created symbolic variables represent real engineering quantities unless a future explicit complex-analysis feature says otherwise.
6. **Piecewise topology is semantic.** `left`/`at`/`right` are emitted only when the topology/value distinction is meaningful.
7. **Units are first-class.** A zero at a dimensional response location inherits the response unit; equivalent unit spellings in supported API positions behave consistently.
8. **Refactor only after GREEN behavior.** Correctness fixes are implemented and validated before splitting `characteristics.py`.
9. **No speculative fixes.** Audit “potential risks” receive tests/investigation first; behavior changes require a reproducible failure.
10. **Preserve released behavior.** All verified 0.9.1 capabilities remain regression requirements, including positive structural moment plotted downward.

## Scope

### In scope

- C-1: root/intersection exact-candidate evaluation and fallback completeness.
- H-1: real-valued SymPy symbol assumptions and all identity-sensitive call sites.
- M-1: unit literals in bounds/domains across `table`, `plot`, `roots`, `intersections`, and `extrema`.
- M-2: Piecewise extrema boundary `value_symbolic` must reflect the selected branch when branch conditions are numerically decidable.
- M-3: continuous Piecewise breakpoints must not emit misleading one-sided points; dimensional zero semantics must be consistent.
- L-1: generic renderer API must handle characteristic results intentionally rather than crashing with `AttributeError`.
- L-2: remove invalid matplotlib `semibold` warning.
- L-3: actionable Piecewise missing-value diagnostics.
- L-4: normalize negative zero and improve exact characteristic coordinate labels without changing mathematical coordinates.
- I-1: permanent GitHub Actions CI.
- I-2: declare IPython consistently with the notebook/magic runtime.
- I-3: validate declared Python `>=3.10` support across 3.10, 3.11, 3.12, 3.13, and 3.14.
- Investigation-only tests for audit potential risks: zero residual tolerance, tri-state `is_real`, and expensive `sp.simplify` candidate paths.
- Behavior-preserving decomposition of the characteristic solver after the defects above are GREEN.
- Full source, wheel, clean-environment, source-free, and post-merge release validation.

### Explicitly out of scope

- Exact envelope crossovers/governing intervals. Deferred to **0.9.3**.
- Named response cases/combinations. Deferred to **0.9.4**.
- `figure(...)` / image embedding.
- `check(...)` or design-code verification APIs.
- Generalized structural eigenproblems.
- Multiline ordinary non-matrix call parsing.
- `no_vertical_scroll()` ergonomics.
- General-purpose complex-variable analysis.
- Replacing the deterministic numeric fallback algorithm with SciPy or adding SciPy as a dependency.

## Public compatibility requirements

The following released calls remain unchanged:

```text
roots(response, variable, lower, upper)
intersections(response_1, response_2, variable, lower, upper)
extrema(response, variable, lower, upper)
plot(...)
table(...)
envelope(...)
```

Characteristic calls remain standalone-only. Whole matrices remain invalid scalar responses; indexed matrix scalars remain valid. Ordinary plots retain the 201-point drawing grid and exact characteristic metadata. `envelope(...)` remains sampled in 0.9.2. Positive structural moment remains plotted downward.

## C-1 — complete and safe root/intersection solving

### Required RED cases

At minimum, the branch must reproduce the following failures before the fix:

```text
f(x) = log(x) - 1
roots(f(x), x, 1, 10)
# expected x = E ≈ 2.718281828...

g(x) = exp(x) - 3*x
roots(g(x), x, 0, 3)
# expected two roots ≈ 0.6190612867 and 1.5121345517

h(x) = x^5 - x - 1
roots(h(x), x, 0, 2)
# expected one root ≈ 1.167303978...

intersections(log(x), 1 + 0*x, x, 1, 10)
# expected x = E
```

Additional regression coverage must include exact candidates represented by `E`, `LambertW`, and `CRootOf`, exact/numeric candidate deduplication, and preservation of exact provenance.

### Closed SymPy numeric evaluation

`NumericContext._evaluate_sympy()` must accept a closed, symbol-free SymPy numeric expression when it evaluates to a real finite number, even if its concrete SymPy class is not one of the currently hand-dispatched classes. This covers objects such as `E`, real `LambertW(...)`, and real `CRootOf(...)`.

The symbolic form is not replaced: exact symbolic objects stay in `x_symbolic`/`value_symbolic`. The generalized numeric path exists only to obtain a Pint-compatible numeric quantity for validation and comparison.

Non-real or non-finite closed expressions remain invalid in real engineering evaluation.

### Exact-discovery completeness

Exact discovery must distinguish **candidate source** from **proof of completeness**.

- `solveset(..., domain=S.Reals)` returning `EmptySet`, `FiniteSet`, or `S.Reals` is authoritative for the corresponding exact topology.
- A fallback call to `sp.solve(...)` may supply useful exact candidates but is **not proof that all real solutions were found**.
- Therefore, candidates obtained from `sp.solve(...)` are retained and validated, while the operation remains `unresolved`/`needs_fallback`.
- Numeric fallback then runs over the physical domain and its results are merged with validated exact candidates.

This is required for expressions such as `exp(x)-3*x`, where a symbolic solver may expose fewer branches than the real domain contains.

### Candidate rejection semantics

Expected mathematical rejections and internal evaluation failures must be distinguished.

Expected rejections include:

- candidate provably non-real;
- candidate outside the requested domain;
- candidate with incompatible dimensions;
- candidate that fails the residual check.

An `EngEvaluationError` caused by EngCalc being unable to numerically evaluate an otherwise plausible closed exact candidate is not evidence that the root does not exist. Such a failure must force unresolved/fallback handling and must not silently become an empty result.

If exact discovery produced plausible candidates, candidate validation encountered internal evaluation failures, and fallback cannot establish a trustworthy final result, EngCalc must raise an actionable `EngEvaluationError` rather than return a confident empty result.

### Merge and deduplication

Exact and numeric points are merged in physical-domain order using existing domain-aware deduplication tolerances. If an exact and numeric point coincide, the exact point is retained. Close but distinct roots such as `(x-1)*(x-1.0000001)` must remain distinct.

### Intersections reuse root semantics

`intersections(f, g, ...)` continues to solve the zero set of `f-g`, but candidate discovery/validation/fallback/merge semantics must share the same core behavior as `roots(...)`. The implementation must not maintain a second subtly different completeness policy.

## H-1 — real engineering symbols

### Symbol contract

All user-facing symbolic variables created by `EngineeringEngine.resolve_symbol(name)` are `sp.Symbol(name, real=True)`.

This applies to independent variables, scalar symbols, and function parameters resolved through the engine. Complex-valued engineering variables are outside 0.9.2 scope.

### Identity audit requirement

Changing symbol assumptions changes SymPy symbol identity. Before the product change, all source locations that recreate a symbol from a string must be audited. Any code that needs to refer to an existing expression variable must reuse the actual expression/engine symbol or create an assumption-compatible symbol deliberately.

In particular, polynomial/partial-evaluation helpers must not construct an assumption-less `sp.Symbol(variable)` that fails to match the engine’s real symbol.

### Required behavior

```text
u(x) = abs(x - 2)
extrema(u(x), x, 0, 4)
```

must return a global minimum at `x=2`, value `0`, without leaking internal `re(...)`, `im(...)`, `Derivative(...)`, or Piecewise parser diagnostics.

Coverage must also include `extrema(abs(M(x)), ...)` for a dimensional response that crosses zero, plus representative existing substitution, polynomial, Piecewise, matrix-index, solve, differentiation, plot, and table regressions after the real-symbol migration.

## M-1 — unit literals in API bounds

Known EngCalc unit aliases may be used directly in bounds/domains anywhere a numeric bound is accepted:

```text
roots(V(x), x, 0*m, 6*m)
extrema(M(x), x, 0*m, 6000*mm)
intersections(M1(x), M2(x), x, 0*m, 6*m)
plot(M(x), x, 0*m, 6*m)
table(M(x), x, 0*m, 6*m, 5)
```

Stored numeric values and explicit overrides take precedence over interpreting a name as a unit alias, preserving the current unit-literal precedence rule used inside characteristic expressions.

Bounds expressed with compatible units normalize to one physical domain. Incompatible dimensions remain errors.

The implementation should centralize unit-literal override resolution rather than copy characteristic-only logic into each API.

## M-2 — Piecewise symbolic boundary values

When a Piecewise condition is numerically decidable from the current context, an extrema boundary point’s `value_symbolic` must be the expression of the branch that actually governs that point, not an unresolved outer `Piecewise(...)` wrapper.

Example:

```text
a := 3*m
L := 6*m
g(x) = piecewise(x-a, x<a, 2*(x-a))
extrema(g(x), x, 0, L)
```

At `x=0`, the exact symbolic value must be `-a`; at `x=L`, it must reflect the second branch (`2*(L-a)` or a mathematically equivalent simplified expression). Numeric quantities stay `-3 m` and `6 m` respectively.

Branch choice may use numeric context, but symbolic output must preserve the user’s symbolic parameters rather than replacing all of them with decimal quantities.

## M-3 — Piecewise continuity and side topology

At an internal Piecewise breakpoint, one-sided characteristic points are emitted only when they encode a real discontinuity or a distinct point value.

- If left limit = point value = right limit after unit normalization, emit one `side="at"` point only.
- If left and right differ, preserve one-sided points as required by the existing discontinuous-Piecewise contract.
- If the explicit value at the breakpoint differs from one or both limits, retain the distinct `at` value plus the meaningful side values.

Dimensionless exact zero is adaptable to the response’s physical unit. The same physical zero must never appear as `0` dimensionless on one side and `0 <unit>` at the same point on another side.

Existing discontinuous Piecewise behavior — including interval openness and left/right semantics — remains a regression requirement.

## L-1 — renderer API coherence

The public/programmatic rendering entry point must not crash when passed `RootsResult`, `IntersectionsResult`, or `ExtremaResult`.

The preferred behavior is intentional dispatch to characteristic rendering while preserving existing return-surface expectations. If the existing generic renderer’s return type cannot safely represent characteristic HTML, the API must fail with an explicit supported-type diagnostic rather than an accidental missing-attribute `AttributeError`. The implementation plan must choose one behavior after inspecting current callers, with backward compatibility preferred.

Notebook `%eng`/`%%eng` behavior must remain unchanged.

## L-2 — matplotlib font weight

Replace unsupported `fontweight="semibold"` usage with a matplotlib-supported equivalent (`600` preferred) so titled plots do not emit font-manager warnings to stderr.

No visual convention change is intended.

## L-3 — actionable Piecewise diagnostics

Piecewise missing-value/unit-literal errors must use the same diagnostic quality as scalar evaluation: identify the missing symbol and give an actionable path to define/fix it. Internal phrases such as “could not be partitioned safely” may remain as technical context but must not be the only user guidance.

## L-4 — characteristic formatting polish

### Negative zero

Values whose magnitude is within the active `RenderSettings.zero_tolerance` render as positive zero. This normalization applies consistently to characteristic output and plot annotations.

### Exact plot coordinates

A plot marker remains positioned using its exact characteristic quantity, never the sampled grid. When an exact compact symbolic coordinate is available (for example `1/3`), the annotation should prefer the symbolic coordinate or show it alongside the configured numeric approximation rather than implying that the authoritative location is merely `0.33`.

This is a presentation change only; the 201-point drawing grid and characteristic math are unchanged.

## I-1 — permanent CI

0.9.2 introduces a permanent checked-in GitHub Actions workflow rather than relying exclusively on temporary release-validation workflows.

Required CI behavior:

- trigger on pull requests and pushes to `main`;
- test Python 3.10, 3.11, 3.12, 3.13, and 3.14;
- install the project from declared metadata (`.[dev]`);
- run `python -m compileall -q src/engcalc_colab`;
- run the complete source suite;
- fail on any version-specific regression.

Release validation remains stricter and still includes a real wheel, external clean-environment smoke, source-free installed-wheel suite, repeated source suite, and cleanup of release-only temporary harnesses. The permanent CI workflow is intentionally retained.

## I-2 — IPython dependency

EngCalc’s notebook magic imports IPython directly. 0.9.2 must declare IPython in project metadata so the environment required by the primary notebook interface is not an undeclared dependency.

Use a lower bound compatible with the declared Python support range; the implementation plan must validate resolver/install behavior on Python 3.10 through 3.14. Tests must stop requiring a separate ad-hoc `pip install ipython` step when the package is installed from its declared metadata.

## I-3 — Python support matrix

The project continues to declare:

```toml
requires-python = ">=3.10"
```

0.9.2 must validate 3.10–3.14 in permanent CI. If a genuine product/dependency incompatibility is found on an advertised version, the preferred response is to fix compatibility. Narrowing `requires-python` requires separate explicit design approval and is not authorized by this spec.

## Audit potential risks — investigation only

The external audit identified three patterns without a confirmed failing reproduction:

1. exact `float(magnitude) == 0.0` residual checks instead of a configured tolerance;
2. tri-state `candidate.is_real` handling when the value is `None`;
3. unbounded cost of `sp.simplify` on large candidate expressions.

0.9.2 must add focused exploratory/regression tests or controlled probes for these patterns. No product change is made solely because the pattern looks risky. If a deterministic failure is reproduced, it becomes a normal RED→GREEN defect within 0.9.2 and is documented in `CURRENT.md`.

## Characteristic solver decomposition

### Timing

The split happens only after C-1, H-1, M-1, M-2, and M-3 are GREEN and the full source suite passes. The split itself is behavior-preserving.

### Target responsibilities

The current monolithic `src/engcalc_colab/characteristics.py` should become a package while preserving this import surface:

```python
from engcalc_colab.characteristics import (
    normalize_analysis_domain,
    solve_roots_exact,
    solve_intersections_exact,
    solve_extrema_exact,
)
```

Recommended responsibility boundaries:

- `characteristics/__init__.py` — stable exports only.
- `characteristics/domain.py` — `AnalysisDomain`, region/domain normalization, unit-literal handling shared by characteristics.
- `characteristics/candidates.py` — exact discovery outcomes, candidate validation, physical ordering/deduplication, exact-vs-numeric merge semantics.
- `characteristics/fallback.py` — deterministic numerical scanning/refinement and residual validation.
- `characteristics/roots.py` — root topology and root-specific result construction.
- `characteristics/intersections.py` — dimensional compatibility plus reuse of root zero-set semantics for `f-g`.
- `characteristics/extrema.py` — stationary/boundary/global/local extrema logic.
- `characteristics/piecewise_analysis.py` — Piecewise region partitioning, side limits, continuity/topology helpers.

Exact file boundaries may be adjusted during planning to avoid circular imports, but responsibilities may not be recombined into another monolith.

### Refactor acceptance

- No public import changes.
- No model/schema changes solely because of the split.
- Focused characteristics suite passes before and after the move.
- Full source suite passes after the move.
- A source-level check ensures the old monolithic module is gone and the stable package exports remain importable.

## Error-handling policy for characteristic candidates

Candidate-processing code must classify outcomes rather than broadly swallowing `EngEvaluationError` into `None`.

At minimum, internal logic must be able to distinguish:

- accepted candidate;
- mathematically rejected candidate;
- candidate outside domain;
- candidate dimensionally incompatible;
- candidate evaluation unresolved/failed and therefore requiring fallback or a diagnostic.

The concrete internal type may be a dataclass/enum or equivalent explicit structure. This is an internal architecture requirement; it must not unnecessarily leak into public result models.

## Testing strategy

### Stage 1 — audit reproduction RED

Create tests that reproduce every confirmed C/H/M defect independently of the external harness. No production patch is allowed before the relevant RED is observed.

### Stage 2 — focused GREEN per defect

Each defect receives the smallest product fix plus focused regressions. Run relevant existing tests after each change.

### Stage 3 — real-symbol migration gate

Because `real=True` changes SymPy identity/assumptions globally, run broad parser/engine/numeric/Piecewise/matrix/CAS/plot/table/characteristic coverage immediately after H-1, not only the new `abs` tests.

### Stage 4 — low-severity cleanup

Add focused tests for renderer dispatch, font warnings, diagnostics, negative zero, and exact characteristic labels.

### Stage 5 — refactor equivalence

Run focused characteristics tests before and after module decomposition, then the complete source suite.

### Stage 6 — permanent CI matrix

Require green Python 3.10–3.14 source jobs before release closure.

### Stage 7 — release validation

The 0.9.2 release gate must include:

- version RED before bump;
- metadata/runtime/README bump to 0.9.2 only at release time;
- compileall;
- complete source suite;
- build `engcalc_colab-0.9.2-py3-none-any.whl`;
- metadata inspection and SHA-256;
- external clean-venv/site-packages smoke including all audit regression cases;
- installed-wheel source-free complete suite;
- repeated source suite;
- cleanup of release-only temporary validation infrastructure;
- PR to `main`;
- explicit user approval before merge;
- post-merge validation on `main`.

## Acceptance cases

0.9.2 is not acceptable unless all of the following hold simultaneously:

1. `roots(log(x)-1, x, 1, 10)` finds `E`/≈2.71828.
2. `roots(exp(x)-3*x, x, 0, 3)` finds both real roots.
3. `roots(x^5-x-1, x, 0, 2)` finds the real root.
4. `intersections(log(x), 1+0*x, x, 1, 10)` finds the intersection.
5. Exact candidates retain exact provenance when merged with fallback results.
6. Existing close distinct roots remain distinct.
7. `extrema(abs(x-2), x, 0, 4)` returns the cusp minimum.
8. A dimensional `abs(M(x))` extrema case works.
9. Existing substitution, Piecewise, matrix/CAS, plotting and table behavior survives real-symbol assumptions.
10. Direct unit literals work consistently in compatible bounds for table/plot/roots/intersections/extrema.
11. Incompatible unit bounds remain rejected.
12. Piecewise boundary `value_symbolic` uses the governing symbolic branch.
13. A continuous Piecewise breakpoint emits only the meaningful `at` value with consistent units.
14. A true discontinuity still exposes correct one-sided topology and interval openness.
15. Generic characteristic rendering no longer crashes accidentally.
16. Titled plots emit no invalid-font-weight warning.
17. Piecewise missing-value diagnostics are actionable.
18. Negative zero is normalized in characteristic presentation.
19. Exact off-grid plot characteristics remain plotted at their exact physical coordinates and labels do not misrepresent the exact location.
20. Permanent CI is green on Python 3.10, 3.11, 3.12, 3.13 and 3.14.
21. IPython is installed through declared project metadata.
22. All 0.9.1 acceptance behavior remains green, including the canonical beam, no false Piecewise jump root, even-multiplicity roots, dimensional guards, indexed matrix scalar characteristics, deterministic numeric fallback, and positive moment plotted downward.
23. `envelope(...)` remains sampled; no exact-envelope API is introduced in this release.
