# EngCalc 0.9.0 — Matrix Numeric Semantics Clarification

**Status:** normative clarification to the 0.9.0 matrix/CAS design  
**Date:** 2026-08-30  
**Applies to:** `2026-08-30-engcalc-v0.9.0-matrix-cas-design.md`

## 1. Purpose

This clarification resolves two ambiguities found during the design self-review:

1. whether `QuantityMatrix` creates a second public matrix algebra beside SymPy;
2. which matrix operations are physically meaningful when a numerical matrix contains heterogeneous units.

This document is normative and must be read together with the main 0.9.0 design spec.

## 2. `QuantityMatrix` is an output boundary, not a second CAS

`QuantityMatrix` is the immutable numerical value produced by matrix-aware numerical evaluation such as:

```text
numeric(A)
```

It is not a second public expression system inside `%%eng`.

The public workflow remains:

```text
EngCalc source
    -> exact symbolic SymPy matrix expression
    -> symbolic matrix algebra
    -> numeric(...)
    -> Pint evaluation of the scalar cells of the resulting symbolic expression
    -> QuantityMatrix final numerical value
```

Therefore 0.9.0 does not duplicate every matrix operator in a separate Pint-backed algebra engine.

For example:

```text
C = A*B
numeric(C)
```

first constructs exact symbolic `C = A*B`. Only when `numeric(C)` is requested are the resulting scalar cell expressions evaluated dimensionally through Pint.

This preserves EngCalc's existing exact-first architecture and prevents divergence between a symbolic matrix engine and a numerical matrix engine.

## 3. Dimensional validation of symbolic matrix algebra

Symbolic matrix algebra may construct formal expressions before physical units are known.

Once `numeric(...)` supplies the Pint-backed scalar bindings, every resulting scalar cell must be dimensionally valid.

For matrix multiplication, each output cell contains a symbolic sum of products. Pint must therefore confirm at numerical evaluation time that all additive terms contributing to that cell have compatible dimensions.

If they do not, numerical evaluation fails with a matrix-specific diagnostic identifying the one-based output coordinate.

The same principle applies to addition, subtraction, determinant expressions, trace expressions, inverses, and solved vectors: exact symbolic construction is allowed; dimensional inconsistency is detected when numerical bindings make the physical dimensions concrete.

## 4. Homogeneous versus heterogeneous numerical matrices

A numerical matrix is **dimensionally homogeneous** when all nonzero entries are compatible with one common physical unit after conversion.

A numerical matrix is **dimensionally heterogeneous** when different entries legitimately carry incompatible dimensions, as in many structural stiffness matrices involving both translational and rotational DOFs.

Exact dimensionless zeros do not by themselves prevent a matrix from being classified as homogeneous when their unit can be inherited unambiguously.

## 5. Operations allowed on heterogeneous dimensional results

The following workflows may produce useful heterogeneous numerical matrices because their output is evaluated cell by cell and does not require one common matrix-wide scale:

- `numeric(A)`;
- matrix indexing followed by `numeric(...)`;
- exact matrix addition/subtraction followed by `numeric(...)`, provided corresponding result cells are dimensionally valid;
- exact matrix multiplication followed by `numeric(...)`, provided each result-cell sum is dimensionally valid;
- exact `det(A)` followed by `numeric(...)`, provided the determinant's additive terms have compatible dimensions;
- exact `trace(A)` followed by `numeric(...)`, provided diagonal terms are dimensionally compatible;
- exact `inv(A)` followed by `numeric(...)`, provided the resulting scalar expressions are dimensionally valid;
- exact `solve(A,b)` followed by `numeric(...)`, provided the solution expressions are dimensionally valid;
- exact matrix-valued user functions followed by `numeric(...)`.

No matrix-wide common unit is assumed for these outputs.

## 6. Operations requiring dimensionless or common-scale numerical matrices

Some algorithms implicitly compare, normalize, combine, or pivot entries across the matrix in a way that has no invariant physical meaning when arbitrary entries carry incompatible dimensions.

Therefore numerical evaluation of the following requires the input matrix to be dimensionless or reducible to one common dimensional scale:

```text
rank(A)
rref(A)
norm(A)
eigenvals(A)
eigenvects(A)
```

If numerical bindings make `A` dimensionally heterogeneous, EngCalc must reject the numerical operation with an explicit engineering diagnostic rather than stripping units or silently converting magnitudes.

Symbolic use of these operations remains available as formal CAS algebra where supported by SymPy.

## 7. Common-scale normalization rule

For an operation that requires one common matrix scale:

1. ignore exact zeros temporarily when discovering candidate dimensionality;
2. require every nonzero entry to be convertible to one common unit;
3. convert entries to that unit;
4. perform the dimensionless numerical algorithm on the matrix of magnitudes;
5. restore physically meaningful units only where the operation has a well-defined unit interpretation.

Examples:

- `norm(A)` of a homogeneous force matrix returns a force quantity;
- `eigenvals(A)` of a homogeneous stiffness-per-length matrix returns eigenvalues carrying that common unit;
- eigenvectors remain dimensionless up to arbitrary scaling;
- `rank(A)` and `rref(A)` operate on normalized magnitudes and return dimensionless structural information / normalized row form;
- a heterogeneous frame-element stiffness matrix must not be forced through this rule.

## 8. `QuantityMatrix` arithmetic visibility

`QuantityMatrix` may implement private helper methods needed for:

- unit normalization;
- target-unit conversion;
- homogeneous-scale detection;
- rendering;
- testing;
- coordinate-aware diagnostics.

Those helpers are implementation details.

0.9.0 does not expose syntax that takes the displayed output of `numeric(A)` and then performs a second public matrix expression on that numerical object.

Users instead write the mathematical expression symbolically first:

```text
C = A*B
numeric(C)
```

not conceptually:

```text
numeric(A) * numeric(B)
```

The latter is not part of the 0.9.0 public contract.

## 9. Target units

`numeric(A, target_unit)` remains valid only when every nonzero final entry is compatible with that one target unit.

For heterogeneous numerical matrices, EngCalc reports that one target unit cannot represent the matrix.

Per-row, per-column, and per-cell target-unit maps remain deferred.

## 10. Acceptance additions

The implementation plan must include RED -> GREEN tests proving:

1. `QuantityMatrix` is a final numeric result and does not create a parallel public algebra syntax;
2. a physically valid heterogeneous stiffness-matrix/vector multiplication can be formed symbolically and evaluated numerically cell by cell;
3. an invalid output-cell sum with incompatible dimensions fails at the correct one-based coordinate;
4. `numeric(rank(A))`, numerical `rref`, numerical `norm`, and numerical eigenanalysis reject heterogeneous dimensional matrices;
5. the same operations accept dimensionless or common-scale numerical matrices where mathematically appropriate;
6. existing scalar numeric evaluation remains unchanged.
