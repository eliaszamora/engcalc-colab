# EngCalc 0.9.0 — Vectors, Matrices, and Linear Systems Design

**Status:** proposed formal specification for user review  
**Date:** 2026-08-30  
**Branch:** `planning/v0.9.0-matrix-cas`  
**Baseline:** EngCalc 0.8.0 on `main@9b90014fa59014eb9e831c71c7f7f2a35dfeb86d`

## 1. Purpose

EngCalc 0.9.0 introduces a calculator/CAS-style matrix subsystem aimed at engineering mathematics rather than general-purpose Python array programming.

The milestone must provide:

- natural matrix and vector notation inside `%%eng`;
- exact symbolic matrix algebra through SymPy;
- numerical matrix evaluation through Pint while preserving physical dimensionality per entry;
- linear-system solution with exact symbolic results first and dimensional numerical evaluation second;
- native MathJax matrix presentation consistent with the existing EngCalc calculation flow;
- explicit engineering diagnostics for shape and dimensionality errors;
- preservation of all 0.8.0 scalar, Piecewise, table, plot, envelope, narrative, and numeric behavior.

The goal is similar in ergonomics to a TI-Nspire CX CAS or MATLAB matrix worksheet while retaining EngCalc's stronger separation between symbolic truth and dimensional numerical truth.

## 2. Architectural classification

This milestone is an architectural extension, not a bounded parser feature.

It introduces:

1. a new expression shape: matrices;
2. new syntax that is intentionally not Python syntax;
3. shape-aware algebra;
4. per-entry dimensional numerical values;
5. matrix-aware rendering;
6. overloaded linear-system solution;
7. matrix-aware versions of selected existing CAS operations.

No production implementation starts until this specification is explicitly approved and a separate implementation plan is written.

## 3. Fundamental language boundary

### 3.1 `%%eng` is not Python

A notebook remains a Python notebook, but a cell beginning with `%%eng` is interpreted by the EngCalc DSL.

Therefore EngCalc is free to support mathematical syntax that Python itself does not accept.

Example:

```text
%%eng

A = [a, b;
     c, d]

v = [x;
     y]
```

The matrix syntax is parsed by EngCalc before any restricted Python AST representation is used for scalar subexpressions.

### 3.2 Python remains available outside `%%eng`

General programming such as loops, imports, pandas, NumPy, SciPy, file I/O, and arbitrary Python remains outside the EngCalc DSL and is performed in ordinary notebook cells.

0.9.0 does not turn `%%eng` into Python and does not permit arbitrary Python statements.

## 4. Canonical matrix literal syntax

### 4.1 Separators

Inside a matrix literal:

- comma `,` starts a new column;
- semicolon `;` starts a new row;
- physical newline is presentation whitespace only while a matrix literal remains open.

Examples:

```text
r = [a, b, c]
```

represents a `1 x 3` row matrix.

```text
v = [a;
     b;
     c]
```

represents a `3 x 1` column matrix.

```text
A = [a, b;
     c, d]
```

represents a `2 x 2` matrix.

These are equivalent:

```text
A = [a, b; c, d]
```

```text
A = [a, b;
     c, d]
```

### 4.2 Commas are mandatory between columns

EngCalc does not accept MATLAB's whitespace-only column syntax:

```text
[a b c]
```

The accepted form is:

```text
[a, b, c]
```

This keeps the grammar deterministic and prevents ambiguity between adjacent scalar expressions.

### 4.3 Rectangularity

Every row must contain the same number of entries.

This is invalid:

```text
A = [a, b;
     c, d, e]
```

The diagnostic must identify the conflicting row widths, for example:

```text
matrix literal rows must have the same number of columns: row 1 has 2, row 2 has 3
```

### 4.4 Empty literals

Empty matrices are not part of the 0.9.0 public literal grammar.

The following are invalid:

```text
[]
[;]
```

Zero-sized matrix construction is not required by this milestone.

### 4.5 Matrix elements

Each matrix cell accepts any scalar EngCalc expression that would otherwise be valid in that expression context, including:

- exact integers and rationals;
- symbols;
- scalar arithmetic;
- scalar user functions;
- supported scalar CAS functions such as `sqrt`, trig, `exp`, and `log`;
- Piecewise scalar expressions;
- exact constants such as `pi`;
- scalar expressions containing numerically assigned symbols.

Examples:

```text
A = [1/3, sqrt(2);
     pi,  x^2]
```

```text
R(theta) = [cos(theta), -sin(theta);
            sin(theta),  cos(theta)]
```

```text
K(E, I, L) = [12*E*I/L^3,  6*E*I/L^2;
               6*E*I/L^2,    4*E*I/L]
```

### 4.6 Nested matrix literals

Matrices of matrices are not supported in 0.9.0.

A matrix cell must evaluate to a scalar symbolic expression, not another matrix.

Block-matrix construction is deferred.

## 5. Contextual meaning of square brackets

EngCalc already uses square-bracket lists in restricted contexts such as explicit `table(...)` points and plot/envelope sweep keyword values.

0.9.0 preserves those existing meanings.

The parser therefore treats square brackets contextually:

- in a normal expression, `[a, b; c, d]` is a matrix literal;
- in an existing `table(...)` explicit-point position, `[x1, x2, x3]` remains a table point collection;
- in a `plot(..., q=[...])` or `envelope(..., q=[...])` sweep keyword, the bracket value remains a sweep collection;
- semicolons are not valid inside table-point or sweep collections.

This avoids breaking the existing 0.8.0 API while allowing row-vector literals in ordinary expressions.

## 6. Multiline statement scanning

Matrix literals require EngCalc to support a restricted multiline statement continuation.

The statement scanner must continue collecting physical lines while an EngCalc matrix literal has unmatched `[` / `]` delimiters.

Example:

```text
K = [12*E*I/L^3, 6*E*I/L^2;
     6*E*I/L^2,   4*E*I/L]
```

is one EngCalc statement.

This continuation rule is scoped to matrix-literal balancing and does not enable arbitrary multiline Python syntax.

Narrative triple-quoted blocks retain their existing independent scanning behavior.

A missing closing bracket must produce a line-aware EngCalc syntax diagnostic rather than a raw Python parser error.

## 7. Internal symbolic representation

### 7.1 Symbolic truth

Symbolic matrices are represented by immutable SymPy matrix objects, preferably `sympy.ImmutableMatrix` or the closest immutable matrix type needed by individual SymPy operations.

EngCalc continues to treat SymPy as the source of symbolic mathematical truth.

### 7.2 Vectors are matrices

0.9.0 does not introduce separate public `Vector`, `RowVector`, and `Matrix` mathematical types.

A vector is represented as a matrix with one row or one column:

- row vector: `1 x n`;
- column vector: `n x 1`.

Consequently shape rules follow matrix algebra directly.

### 7.3 Scalar result collapse

A `1 x 1` matrix produced by matrix multiplication remains a matrix result unless the operation is explicitly defined to return a scalar, such as `det`, `trace`, or indexing.

This keeps matrix shape semantics stable and avoids silent type collapse.

## 8. Matrix assignment and state

### 8.1 Symbolic assignment

Standard `=` stores symbolic matrices in the same symbolic namespace model as scalar expressions, with matrix-aware value handling.

Examples:

```text
A = [a, b;
     c, d]
```

```text
K = [k1 + k2, -k2;
     -k2,       k2]
```

### 8.2 Numeric matrix assignment operator

0.9.0 does not initially extend scalar `:=` into a second persistent matrix state.

Fully numeric matrices are obtained naturally by assigning symbols numerically and using `numeric(...)`:

```text
E := 200*GPa
I := 450e6*mm^4
L := 6*m

K = [12*E*I/L^3, 6*E*I/L^2;
     6*E*I/L^2,   4*E*I/L]

numeric(K)
```

This preserves the current architecture in which `=` is symbolic state and `:=` is Pint-backed scalar state.

A future matrix-valued `:=` may be considered only if user workflows demonstrate a real need.

## 9. Indexing

### 9.1 One-based indexing

EngCalc uses mathematical/MATLAB-style one-based indexing.

For:

```text
A = [a, b;
     c, d]
```

```text
A[1, 1]
```

returns `a`, and:

```text
A[2, 1]
```

returns `c`.

### 9.2 Vector shorthand

For a row or column vector only, one index is accepted:

```text
v = [a;
     b;
     c]

v[2]
```

returns `b`.

The same shorthand applies to a `1 x n` row vector.

### 9.3 General matrices require two indices

A general `m x n` matrix with both dimensions greater than one requires two indices.

`A[2]` on a `2 x 2` matrix is an explicit EngCalc error rather than implicit flattening.

### 9.4 Index constraints

Indices must be exact positive integers.

Invalid cases include:

- zero;
- negative indices;
- floats;
- symbolic indices in 0.9.0;
- out-of-range indices;
- more than two indices.

Diagnostics must report the matrix shape and requested index when useful.

### 9.5 Slicing

Row/column slicing such as `A[1,:]`, `A[:,2]`, and submatrix slices are outside 0.9.0.

## 10. Core algebraic operators

### 10.1 Addition and subtraction

`A + B` and `A - B` require identical shapes.

For numerical matrices, corresponding cells must also be dimensionally compatible.

Exact dimensionless zeros may adapt to a compatible physical unit where unambiguous.

### 10.2 Scalar multiplication and division

The following are supported:

```text
c*A
A*c
A/c
```

where `c` is scalar.

A matrix divided by a matrix is not defined through `/`.

### 10.3 Matrix multiplication

`A*B` means matrix multiplication whenever both operands are matrices.

It requires:

```text
A.shape = m x n
B.shape = n x p
```

and produces `m x p`.

The diagnostic for a shape mismatch must explicitly show the two shapes, for example:

```text
matrix multiplication dimension mismatch: left is 2x3, right is 2x2
```

### 10.4 Matrix-vector multiplication

Because vectors are matrices, matrix-vector and vector-matrix multiplication use the same rule.

For:

```text
r = [a, b, c]
v = [x;
     y;
     z]
```

`r*v` is `1 x 1` and `v*r` is `3 x 3`.

### 10.5 Matrix powers

For square matrices, integer matrix powers are supported:

```text
A^2
A^3
A^0
A^-1
```

EngCalc's existing normalization of `^` to `**` remains an implementation detail.

Rules:

- exponent must be an exact integer;
- matrix must be square;
- `A^0` returns the identity of matching size;
- `A^-1` is equivalent to `inv(A)` and fails for singular matrices;
- non-integer and symbolic matrix powers are outside 0.9.0.

### 10.6 Scalar-matrix mixed addition

`A + c` and `c + A` are not supported in 0.9.0, even if a backend library provides some convention.

This avoids confusing element-wise semantics.

### 10.7 Element-wise matrix operations

Element-wise multiply/divide/power operators are not introduced in 0.9.0.

The milestone is linear algebra, not NumPy-style array programming.

## 11. Core constructors

The following constructors are part of the 0.9.0 public API:

```text
identity(n)
zeros(m, n)
diag(a, b, c, ...)
```

### 11.1 `identity(n)`

Returns an exact `n x n` symbolic identity matrix.

`n` must be an exact positive integer resolvable at symbolic evaluation time.

### 11.2 `zeros(m, n)`

Returns an exact `m x n` symbolic zero matrix.

Both dimensions must be exact positive integers.

### 11.3 `diag(...)`

Creates a square diagonal matrix from one or more scalar expressions.

Example:

```text
D = diag(k1, k2, k3)
```

produces `3 x 3`.

### 11.4 Deferred constructors

`ones`, block matrices, sparse constructors, and reshape utilities are deferred.

## 12. Core matrix functions

The mandatory 0.9.0 core includes:

```text
transpose(A)
det(A)
inv(A)
trace(A)
rank(A)
rref(A)
norm(A)
size(A)
eigenvals(A)
eigenvects(A)
```

### 12.1 `transpose(A)`

Returns the exact matrix transpose.

### 12.2 `det(A)`

Requires a square matrix and returns an exact scalar symbolic expression.

### 12.3 `inv(A)`

Requires a square, nonsingular matrix and returns an exact symbolic matrix when possible.

A singular matrix produces an EngCalc diagnostic rather than leaking a backend exception.

### 12.4 `trace(A)`

Requires a square matrix and returns a scalar symbolic expression.

### 12.5 `rank(A)`

Returns an exact integer when SymPy can determine it under the current symbolic assumptions.

0.9.0 does not introduce a symbolic-assumption UI to resolve ambiguous rank cases.

### 12.6 `rref(A)`

Returns the reduced row-echelon matrix as the principal displayed result.

Pivot-column metadata from SymPy may be retained internally for testing or future use but is not required as a second public output in 0.9.0.

### 12.7 `norm(A)`

The initial matrix norm is the Frobenius norm.

For a vector it therefore corresponds to the Euclidean norm.

Alternative norm selectors are deferred.

### 12.8 `size(A)`

Returns matrix shape information in a renderer-supported mathematical form.

The internal representation may be a small immutable shape result rather than a Python tuple exposed directly to users.

Examples:

- `size([a,b,c])` -> `(1,3)`;
- `size([a;b;c])` -> `(3,1)`.

### 12.9 `eigenvals(A)` and `eigenvects(A)`

These support exact symbolic matrices and suitable numerical matrices.

Their public result representation must be deterministic and renderer-friendly.

For repeated eigenvalues, multiplicities must not be silently discarded.

The implementation plan must define concrete result models before production coding.

## 13. Secondary factorizations within the milestone

After the core matrix semantics, numerical dimensional matrix handling, solving, and rendering are stable, 0.9.0 may add:

```text
lu(A)
qr(A)
cholesky(A)
```

These are lower priority than the core and must not block the first usable matrix subsystem.

Rules:

- symbolic use follows mathematically appropriate SymPy operations;
- numerical dimensional use is allowed only when the decomposition is dimensionally meaningful under the matrix normalization rules defined below;
- `cholesky` requires a suitable square positive-definite matrix;
- decomposition-specific multiple-output UI must be defined before each function is exposed.

If implementation complexity threatens the milestone, these factorizations may move to 0.9.x without changing the core 0.9.0 acceptance contract.

## 14. Existing CAS functions applied to matrices

Where mathematically unambiguous, selected existing EngCalc functions become matrix-aware.

### 14.1 Element-wise symbolic transforms

The following apply independently to every matrix element:

```text
simplify(A)
expand(A)
factor(A)
subs(A, x, value)
diff(A, x)
integral(A, x, lower, upper)
```

The result remains a matrix of the same shape.

### 14.2 Scalar-only functions remain scalar-only

Functions such as scalar trig calls do not automatically become element-wise matrix functions in 0.9.0.

For example, `sin(A)` is not interpreted as element-wise sine and is not interpreted as the matrix sine.

Matrix functions such as matrix exponential are deferred and must receive dedicated names/semantics if added later.

## 15. Matrix-valued user functions

User-defined functions may return matrices.

Example:

```text
R(theta) = [cos(theta), -sin(theta);
            sin(theta),  cos(theta)]
```

Example:

```text
k(E, I, L) = [12*E*I/L^3, 6*E*I/L^2;
               6*E*I/L^2,   4*E*I/L]
```

Calling a matrix-valued function symbolically returns an exact symbolic matrix.

Calling it through `numeric(...)` evaluates each resulting entry with the existing function-argument binding rules and numeric shadowing semantics.

The existing exact arity rules for multi-argument user functions remain unchanged.

## 16. Numerical matrix architecture

### 16.1 Separation of symbolic and numerical truth

EngCalc preserves the existing architectural rule:

- SymPy owns exact symbolic expressions and matrices;
- Pint owns physical units and numerical dimensional values.

Pint quantities are not embedded as symbolic unit atoms into SymPy matrices.

### 16.2 `QuantityMatrix`

0.9.0 introduces an internal immutable numerical matrix value, referred to in this specification as `QuantityMatrix`.

Each matrix cell contains a Pint-compatible scalar quantity.

The matrix stores:

- row count;
- column count;
- immutable ordered entries;
- per-entry dimensionality;
- optional derived normalization metadata for rendering.

No assumption is made that every entry shares one unit.

### 16.3 Why per-entry units are required

Engineering matrices can be dimensionally heterogeneous.

For example:

```text
K = [12*E*I/L^3, 6*E*I/L^2;
     6*E*I/L^2,   4*E*I/L]
```

contains entries proportional to:

- force / length;
- force;
- force * length.

Representing the entire matrix with one Pint unit would be physically wrong.

### 16.4 Numerical matrix evaluation

`numeric(A)` evaluates each symbolic matrix entry through `NumericContext` using the same scalar numerical rules already used by EngCalc.

It returns a matrix-specific numerical evaluation result whose final value is a `QuantityMatrix`.

### 16.5 Target-unit conversion

A single scalar target unit in:

```text
numeric(A, kN)
```

is allowed only when every nonzero matrix entry is dimensionally compatible with that target unit.

This is useful for homogeneous matrices.

For a heterogeneous matrix, a single target-unit conversion fails with an explicit diagnostic.

0.9.0 does not introduce per-row, per-column, or per-cell target-unit maps.

## 17. Dimensional zero rules

Exact zero retains the dimensional adaptability already established by scalar and Piecewise numerical evaluation.

Examples such as:

```text
A = [k1, 0;
     0,  k2]
```

must not fail simply because the symbolic zeros begin dimensionless.

However zero inheritance must be local and unambiguous.

The numerical matrix layer may infer a zero's working unit from the operation context, such as:

- an addition with a dimensional term;
- a homogeneous output cell;
- a homogeneous row/column normalization used only for rendering.

It must not invent a physical dimension when no compatible context exists.

## 18. Numerical matrix addition and subtraction

For `A + B` and `A - B`:

1. shapes must match;
2. corresponding entries are combined independently;
3. Pint enforces dimensional compatibility per cell;
4. an exact dimensionless zero may adopt the counterpart's unit;
5. any incompatible cell fails the whole operation with a diagnostic containing the failing matrix coordinate using one-based indexing.

Example diagnostic:

```text
matrix addition has incompatible units at [2,1]
```

## 19. Numerical matrix multiplication dimensional rules

For:

```text
C = A*B
```

entry `C[i,j]` is:

```text
sum_k A[i,k] * B[k,j]
```

Each product term may have its own computed unit, but all terms being added into one result cell must be dimensionally compatible.

This rule is essential for engineering systems with mixed translational and rotational degrees of freedom.

If the products contributing to one output cell are dimensionally incompatible, the multiplication fails with a diagnostic identifying the result coordinate and conflicting term dimensions.

No global requirement is imposed that different result cells share the same dimensions.

## 20. Linear systems

### 20.1 Public syntax

EngCalc overloads the existing `solve` function by operand shape.

Existing scalar form remains:

```text
solve(equation, x)
```

New matrix form is:

```text
solve(A, b)
```

when the first argument is a matrix and the second is a compatible column matrix/vector.

### 20.2 Symbolic solve

For symbolic matrices, `solve(A,b)` solves:

```text
A*x = b
```

for the implicit unknown column vector `x` and returns the exact symbolic solution vector.

Example:

```text
K = [k1 + k2, -k2;
     -k2,       k2]

F = [P;
     0]

u = solve(K, F)
```

returns an exact `2 x 1` symbolic matrix.

### 20.3 Shape rules

For `A` of shape `m x n`, the initial 0.9.0 linear-system form requires:

- `A` square (`n x n`);
- `b` a column matrix of shape `n x 1`;
- a unique solution.

Rectangular least-squares systems are deferred.

Multiple right-hand sides are deferred from the public `solve(A,B)` contract for 0.9.0 unless implementation proves trivial after the single-column solver is complete.

### 20.4 Singular and underdetermined systems

A singular matrix must not yield an arbitrary solution.

EngCalc reports whether the system is singular/no-unique-solution using a domain-specific diagnostic.

Parametric solution families are outside the initial matrix solver contract.

### 20.5 Dimensional numerical solve

A critical acceptance case is:

```text
K = [k1 + k2, -k2;
     -k2,       k2]

F = [P;
     0]

u = solve(K, F)

k1 := 20*kN/mm
k2 := 15*kN/mm
P  := 30*kN

numeric(u)
```

The exact symbolic solution is produced first; numerical evaluation then resolves displacement quantities through Pint.

For more general heterogeneous engineering systems, the numerical result may contain different dimensions by component when mathematically appropriate.

### 20.6 No hidden float solve

EngCalc must not silently convert exact symbolic systems to floating-point NumPy solves as the default CAS path.

Numerical fallback may be introduced later for explicitly numerical large systems, but it is not the semantic basis of 0.9.0.

## 21. Eigenvalues and eigenvectors

### 21.1 Symbolic matrices

`eigenvals(A)` and `eigenvects(A)` are allowed for symbolic matrices supported by SymPy.

Exact results are preferred.

### 21.2 Dimensionless and homogeneous numerical matrices

Numerical eigenvalue/eigenvector evaluation is allowed when the matrix has a meaningful common dimensional scaling.

A homogeneous physical unit may be factored conceptually before the dimensionless eigenproblem, with the eigenvalues carrying that unit when mathematically appropriate.

### 21.3 Heterogeneous dimensional matrices

A general heterogeneous physical matrix does not have a standalone conventional eigenproblem with one uniform eigenvalue dimension.

Therefore numerical `eigenvals` / `eigenvects` on such a matrix must fail with an engineering diagnostic rather than stripping units.

### 21.4 Generalized structural eigenproblem

The structural modal problem:

```text
K*phi = lambda*M*phi
```

is a generalized eigenproblem and is outside 0.9.0.

It should later receive an explicit API rather than being misrepresented as `eigenvals(K)`.

## 22. Rendering

### 22.1 Symbolic matrices

Matrices render as native MathJax/LaTeX matrices, for example:

```latex
\begin{bmatrix}
... \\
...
\end{bmatrix}
```

Users must never see raw backend representations such as:

```text
Matrix([[...], [...]])
```

in normal EngCalc output.

### 22.2 Assignment rendering

A symbolic matrix assignment should render in the existing equation-group style:

```text
K = [ ... ]
```

as a mathematical matrix, preserving source order with surrounding scalar calculations.

### 22.3 Numerical homogeneous matrices

If every nonzero entry is dimensionally compatible with one display unit, the renderer may factor the unit outside the matrix:

```text
[ 20  -20 ] kN/mm
[-20   20 ]
```

subject to existing precision and zero-tolerance settings.

### 22.4 Numerical heterogeneous matrices

If entries have heterogeneous dimensions, each cell displays its own unit.

No fake common unit is introduced.

### 22.5 `numeric(...)` workflow

Matrix numerical rendering should follow the conceptual scalar EngCalc flow:

1. symbolic expression / matrix;
2. substitution state when informative and visually tractable;
3. final numerical matrix.

The renderer may suppress a fully expanded substitution matrix when doing so would create unreadable duplication, provided the exact symbolic matrix and final numerical matrix remain visible.

Detailed adaptive layout thresholds belong in the implementation plan and renderer tests rather than this design spec.

### 22.6 Large matrices

0.9.0 targets small and medium engineering matrices suitable for notebook display.

The renderer may use compact formatting for larger matrices but must not silently truncate values without an explicit visible indication.

Sparse/global FEM matrix visualization is outside the milestone.

## 23. Result models

Production implementation should introduce explicit matrix-aware result boundaries rather than overloading scalar fields with undocumented polymorphism.

Likely model families include:

- symbolic matrix evaluation result compatibility through `EvaluationResult` where safe;
- a matrix-specific numerical evaluation result or generalized numeric result capable of holding `QuantityMatrix`;
- deterministic eigenvalue/eigenvector result models;
- deterministic decomposition result models if LU/QR/Cholesky ship in 0.9.0.

The implementation plan must decide exact dataclass names and fields before TDD tasks that depend on them.

## 24. Parser architecture

### 24.1 Do not make Python AST parse matrix syntax directly

The source form:

```text
[a, b; c, d]
```

is intentionally not Python.

EngCalc must recognize matrix literals before handing scalar pieces to Python's restricted AST machinery.

### 24.2 Dedicated matrix literal scanner/parser

The recommended flow is:

```text
raw %%eng text
    -> statement scanner
    -> matrix-literal recognition and balanced-delimiter parsing
    -> split top-level rows on ';'
    -> split top-level cells on ','
    -> parse every cell with existing scalar EngCalc normalization/AST validation
    -> construct an internal matrix-literal node or safe placeholder
    -> symbolic evaluation to ImmutableMatrix
```

Top-level separators inside nested scalar parentheses or function calls must not split a matrix cell.

Example:

```text
A = [f(a, b), g(c);
     h(d),    k(e, f)]
```

contains two columns, not extra columns from function-call commas.

### 24.3 Restricted internal representation

The matrix parser may create a private EngCalc AST/model node instead of translating matrix literals into a fake public function call.

The implementation should prefer an explicit private representation if it makes validation and diagnostics clearer.

### 24.4 Nested brackets in existing list contexts

Context-specific table/sweep lists remain parsed by their existing restricted collection logic.

The matrix parser must not reinterpret those collections as matrices.

## 25. Error handling contract

Matrix errors must be EngCalc diagnostics with line context where appropriate.

Mandatory diagnostic categories include:

- unclosed matrix literal;
- empty matrix literal;
- inconsistent row width;
- unsupported nested matrix;
- non-scalar matrix cell;
- matrix shape mismatch for addition/subtraction;
- matrix multiplication shape mismatch;
- nonsquare operation where square is required;
- singular inverse;
- invalid matrix exponent;
- invalid one-based index;
- out-of-range index;
- incompatible units at a matrix coordinate;
- incompatible dimensional products in a matrix multiplication output cell;
- heterogeneous matrix cannot use one target unit;
- no unique linear-system solution;
- heterogeneous dimensional matrix cannot use ordinary numerical eigen analysis.

Raw SymPy, Pint, NumPy, or Python parser exceptions must not escape as the primary user-facing error.

## 26. Interaction with Piecewise

Piecewise scalar expressions may appear inside matrix cells.

Example:

```text
K(x) = [piecewise(k1, x < L/2, k2), 0;
        0,                            k3]
```

`numeric(K(x0))` evaluates each cell through the existing Piecewise numerical semantics.

0.9.0 does not introduce matrix-valued `piecewise(...)` branches unless they fall out safely from SymPy and the matrix result model without additional grammar or dimensional ambiguity.

Matrix-valued Piecewise should be treated as deferred unless explicitly covered by implementation tests.

## 27. Interaction with tables, plots, and envelopes

### 27.1 Tables

Existing engineering tables remain scalar-response tables in 0.9.0.

Passing a full matrix as one table response is outside the milestone.

Users may table individual indexed entries, for example conceptually:

```text
table(K(x)[1,1], x, ...)
```

once matrix indexing is implemented.

### 27.2 Plots

Existing `plot(...)` and `envelope(...)` remain scalar-response APIs.

A matrix cannot be plotted directly in 0.9.0.

Users plot indexed scalar entries or separately defined scalar responses.

### 27.3 Sweep lists

Existing plot/envelope sweep list syntax remains unchanged and contextually distinct from row-vector literals.

## 28. Compatibility requirements

0.9.0 must preserve all existing public behavior outside the newly defined matrix syntax.

In particular:

- scalar `solve(eq,x)` remains unchanged;
- scalar `numeric(...)` and `result(...)` remain unchanged;
- multi-argument user functions remain unchanged;
- scalar `diff`, `integral`, `subs`, `simplify`, `expand`, and `factor` retain their behavior;
- Piecewise syntax and diagnostics remain unchanged;
- table explicit point lists remain collections, not row matrices;
- plot/envelope sweep lists remain collections;
- positive structural moment remains downward;
- narrative and presentation behavior remain unchanged;
- `%%eng` remains a restricted DSL and does not execute arbitrary Python.

## 29. Performance and scope assumptions

The 0.9.0 design targets notebook-scale engineering mathematics rather than production finite-element global solvers.

Acceptance should prioritize correctness for matrices roughly in the range encountered in hand calculations, element matrices, transformations, small structural systems, educational eigenproblems, and symbolic derivations.

No hard matrix-size cap is specified at design time, but the implementation must not promise efficient dense symbolic algebra for very large matrices.

## 30. Explicitly deferred features

The following are not part of the mandatory 0.9.0 acceptance contract:

- arbitrary Python/NumPy code inside `%%eng`;
- NumPy-style broadcasting;
- element-wise matrix operators;
- row/column slicing and submatrix ranges;
- symbolic matrix indices;
- block-matrix literals;
- sparse matrix literals and sparse solvers;
- global FEM matrix assembly;
- large-system optimized numerical solvers;
- least-squares / rectangular system solve;
- pseudoinverse;
- SVD;
- matrix exponential/logarithm/trigonometric functions;
- generalized eigenproblems such as `K phi = lambda M phi`;
- automatic structural DOF dimensional metadata;
- per-cell target-unit maps;
- matrix-valued persistent `:=` assignments;
- automatic plotting or tabulation of whole matrices;
- complex-frequency/dynamic matrix special handling;
- assumption UI for symbolic rank/eigen ambiguity.

## 31. Mandatory acceptance examples

### 31.1 Literal orientation

```text
r = [a, b]
v = [a;
     b]
```

must produce shapes `1 x 2` and `2 x 1` respectively.

### 31.2 Exact symbolic inverse

```text
A = [a, b;
     c, d]

inv(A)
```

must remain exact and render mathematically.

### 31.3 Exact structural solve

```text
K = [k1 + k2, -k2;
     -k2,       k2]

F = [P;
     0]

u = solve(K, F)
```

must produce an exact symbolic `2 x 1` solution.

### 31.4 Dimensional numerical solve

With:

```text
k1 := 20*kN/mm
k2 := 15*kN/mm
P  := 30*kN
```

`numeric(u)` must return displacement quantities with a length dimension.

### 31.5 Heterogeneous structural matrix

```text
K = [12*E*I/L^3, 6*E*I/L^2;
     6*E*I/L^2,   4*E*I/L]
```

must numerically evaluate without forcing one unit onto all entries.

### 31.6 Dimensionally valid mixed-DOF multiplication

A stiffness-like heterogeneous matrix multiplied by a vector containing a translation and a rotation must permit a physically valid result whose rows may have force and moment dimensions respectively.

### 31.7 Dimensionally invalid multiplication

If the sum of products contributing to one result cell has incompatible dimensions, the operation must fail and identify that output cell.

### 31.8 One-based indexing

```text
A = [a, b;
     c, d]

A[2,1]
```

must return `c`; index zero must be rejected.

### 31.9 Existing table-list compatibility

Existing `table(..., [0*m, 1*m, 2*m])` behavior must remain a point list and must not become a row matrix.

### 31.10 Existing sweep compatibility

Existing `plot(..., q=[1*kN, 2*kN])` and envelope sweep behavior must remain unchanged.

### 31.11 MathJax rendering

Symbolic and numerical matrix results must render as matrices, not raw Python/SymPy container text.

### 31.12 Distribution validation

The final 0.9.0 release must repeat EngCalc's established release standard:

- focused RED -> GREEN evidence per task;
- complete source suite GREEN;
- built wheel with correct version metadata;
- installation into a clean external virtual environment;
- smoke import from `site-packages` rather than the repository source tree;
- complete source-free suite against the installed wheel;
- final source-suite recheck;
- no merge to `main` without explicit user approval.

## 32. Recommended implementation boundaries

The detailed implementation plan should preserve small, testable components. A likely decomposition is:

1. matrix statement/literal scanning and private parsed model;
2. symbolic matrix construction and one-based indexing;
3. symbolic algebra/operators and constructors;
4. matrix-aware user functions and existing CAS transforms;
5. `QuantityMatrix` and per-entry numeric evaluation;
6. dimensional matrix arithmetic;
7. symbolic and dimensional `solve(A,b)`;
8. eigen/rref/rank/norm result models;
9. native matrix MathJax rendering;
10. acceptance/regression/distribution validation;
11. optional LU/QR/Cholesky only after the core is stable.

This decomposition is guidance for the later implementation plan, not authorization to start production work.

## 33. Final design decisions

The following decisions are explicit and normative for this specification:

- `%%eng` remains an EngCalc DSL, not Python.
- Matrix input uses `[a, b; c, d]` syntax.
- Commas separate columns; semicolons separate rows.
- Physical line breaks inside an open matrix literal are presentation only.
- Vectors are matrices of shape `1 x n` or `n x 1`.
- No mandatory `vector()` or `row()` constructors exist.
- Matrix indexing is one-based.
- Symbolic matrices use immutable SymPy matrix semantics.
- Numerical matrices use a per-entry Pint quantity representation.
- Heterogeneous physical units inside one matrix are first-class and must not be flattened into one fake unit.
- Exact zero may inherit a compatible unit only when context makes that inheritance unambiguous.
- `A*B` is matrix multiplication.
- `solve(A,b)` is the canonical linear-system API.
- Exact symbolic solving precedes dimensional numerical evaluation.
- `numeric(A)` is the canonical numerical matrix evaluation path in 0.9.0.
- Matrix-valued `:=` state is deferred.
- Existing table and sweep bracket lists retain their current contextual collection semantics.
- Existing scalar and Piecewise behavior must remain regression-compatible.
- Matrix/CAS 0.9.0 does not include generalized structural eigenproblems, sparse FEM workflows, or NumPy-style array programming.
